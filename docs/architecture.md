# Architecture

## Project Identity

The current project brand is `die Nische`, with the short description `A KDE 3-inspired web desktop.` It is an independent project; KDE 3, KDE, and the recreated application names remain historical/design references rather than a parent brand. Stable application IDs, persistence keys, VFS namespaces, and theme identifiers are compatibility data and are not renamed for presentation.

## Konqueror Media Navigation

- Supported Media tabs expose one shared `play`, `pause`, `stop`, `previous`, and `next` command vocabulary to the client-area transport strip and the media-only Player application menu. The Player menu is inserted between Bookmarks and Tools only while the active tab is media.
- Previous and Next project the current file's direct parent through the active Konqueror directory sort authority, filter the resulting order through `isKonquerorMediaFile`, and never wrap. A destination is opened with the existing `navigateToFileNodeId` path, so the normal per-tab history records it, the old element is paused during unmount, and the new media starts paused. Missing parents or stale files expose no adjacent target.
- Play, Pause, and Stop availability is derived from the media load state in one pure helper. Play resets ended/stopped media through the existing media element path; Pause only pauses; Stop retains its existing pause-and-reset behavior. No playlist, autoplay-next, global media state, or toolbar playback controls are introduced.

## Konqueror Document Resources

`SafeVfsDocumentBody` is the shared read-only renderer for local KHTML, Markdown, and Article Reader bodies. Explicit HTML5 `video`, `audio`, and `source` nodes use `documentResourceResolver` for source-relative `src`, `<source src>`, and video `poster` references. The resolver returns VFS `asset-url` values or the existing HTTPS allowlist; it never promotes a virtual path, text file, `javascript:`, `data:`, `file:`, empty, or query-bearing reference to a browser source. Ordinary Markdown links, bare URLs, fenced code, and escaped tags remain non-media text. The safe attribute set retains native controls and bounded playback hints, excludes autoplay and event handlers, and preserves fallback text. Scoped document/article CSS keeps media within the existing scroll surface without cropping. Direct media-file navigation remains owned by `KonquerorMediaView`.

## Desktop Shell

The runtime theme is one applied `DesktopPreferences.themeId` value selected from the two-entry `themeCatalog`: `kde-classic` (`KDE_Classic`) and `redmond` (`Redmond`). The preference remains in the existing versioned DesktopPreferences record; missing or unsupported theme ids normalize to `KDE_Classic` without creating a second store. `ThemeDomAuthority` mirrors the applied value to `html[data-kde-theme]`, which is the global CSS authority inherited by the Desktop shell and its shell-owned popup layers. Standard application and dialog push buttons use the shared `kde-raised` primitive; menu rows, titlebar controls, toolbar buttons, and document/content surfaces retain their own presentation roles.

`KDE_Classic` keeps the accepted raised/pressed button, chrome, titlebar, Kicker, K Menu, and context-menu token values. Kicker is shell-global KDE Classic chrome: its face, launchers, task buttons, pager, Clipboard, Clock, K Menu, and panel bevels do not inherit Redmond overrides. `Redmond` changes application/window presentation tokens to solid neutral gray, a horizontal dark-blue-to-light-blue active title, stronger light/dark bevels, dark separators, and blue/navy menu selection. It does not remount applications, alter Window Manager records, or change the configured/requested `1.4` UI scale and geometry semantics. Browsers may quantize the applied CSS `zoom`; the responsive provider reads that effective `.desktop-shell` value for all CSS-pixel/logical conversions without modeling browser page zoom. White document/editor/file/tree surfaces, terminal black, authored content, wallpaper, icons, and font metrics remain semantic content or existing workspace presentation rather than theme-managed state.

Owns the full-viewport desktop surface, background, desktop icons, managed prototype windows, and the Kicker panel. The shell boots the Window Manager with an empty window session and renders a window layer through the provider.

Desktop stacking layers:

1. Desktop background.
2. Desktop icons.
3. Application window layer.
4. Kicker.
5. Shell transient popup layer.
6. Lock and session overlays.
7. Future system overlays such as tooltips or modal surfaces.

`desktop-shell` is an isolated root stacking context. `ResponsiveLayoutProvider` measures the unzoomed `#root`, resolves the browser-applied shell zoom, and publishes one logical viewport/work-area snapshot to both WindowManager and semantic root CSS variables. `DesktopWindowLayer` renders all `WindowFrame` nodes inside `.desktop-window-layer`, which is a sibling of the Kicker rather than a parent or child. The window layer is positioned over the work area above the panel and has a lower layer token than `.kicker`.

Window geometry has three distinct policies:

- Initial placement and deterministic cascade use the `WorkArea`, keeping new normal windows inside the usable desktop region.
- Maximized windows use the exact `WorkArea` and always stop at the Kicker top edge.
- Normal titlebar drag uses the full `ScreenArea` recovery policy. A centralized `MIN_VISIBLE_TITLEBAR_WIDTH` keeps a draggable titlebar strip on screen while allowing left/right overflow and a body that extends behind Kicker and below the viewport. The titlebar top cannot move above the screen, and its bottom remains at or above the Kicker edge.

Normal drag and resize write their partial-offscreen coordinates and dimensions into canonical `DesktopWindow.bounds`; neither is a CSS-only transform. Minimize/restore, virtual-desktop moves, Show Desktop, Lock, task activation, and maximize `restoreBounds` retain those bounds. On viewport shrink, normal bounds and stored normal `restoreBounds` are reclamped only to the recovery position contract, not back into the full WorkArea, and oversized normal dimensions are retained. No snapping, tiling, magnetic edges, or window-position persistence is introduced.

Window Manager z-index values only sort windows inside `.desktop-window-layer`. They do not compete with the Kicker, because the Kicker is a higher sibling stacking context. This avoids relying on a huge panel z-index or clamping `nextZIndex` to a magic number. `DesktopTransientPopupLayer` is a shell-root sibling above Kicker and below system overlays. Window-owned, desktop-owned, titlebar, and grouped-task transient surfaces render there while retaining their logical owner tree; K Menu and Klipper keep their existing panel ownership and upward geometry. The ordering is normal windows < Kicker < transient popups < Lock/session overlays.

Desktop icons:

- `desktopIconModel.ts` defines the readonly desktop icon definitions.
- Each definition has a stable id, label, icon id, action, and initial column/row.
- `label` is the semantic and accessible name.
- Optional `labelLines` are visual-only layout hints used to prevent unstable browser wrapping.
- The current actionable set is Trash and My Computer; Desktop Home remains an explicit desktop context action.
- Desktop Home, Trash, and My Computer are explicit Konqueror launchers. They use `launchNewApplicationInstance` with their existing Home, `trash:/`, or `sysinfo:/` intent; Trash derives its empty/full icon state from the shared VFS directory.
- CD/DVD-ROM and Floppy remain placeholders. Placeholder icons can be focused and selected, but activation has no side effect.
- `desktopIconSelectionReducer` owns local desktop selection state; ordinary clicks keep one primary selection while marquee selection preserves the ordered selected ID set, and neither is part of the Window Manager or Application Runtime.
- Single click selects an icon only.
- Double click launches only actionable icons. Explicit desktop location launchers create a new Konqueror instance without changing their established location intent.
- Clicking desktop background, windows, or the panel clears desktop icon selection without preventing the target interaction.
- Keyboard support covers Enter to activate, Space to select, Escape to clear selection, and ArrowUp/ArrowDown to cycle the vertical icon list.
- Icon dragging, multi-select, box select, grid snapping, persistence, and desktop files are intentionally not implemented.

## Kicker

The historical `about-kde`, project `about-die-nische`, and app-specific `about-konqueror` and `about-kcontrol` registrations are independent singleton normal windows: launch requests focus or restore the matching existing window, they can coexist, and none creates a modal relationship with its originating application. `About KDE` keeps the historical KDE context, while `About die Nische` owns the project Overview/Legal/Licenses surface. Konqueror Help routes exactly `About Konqueror` then historical `About KDE` to those stable app ids; the Kicker Quick Launch strip does not duplicate either About launcher.

Represents the KDE 3 style bottom panel. It includes the K menu button, current quick launch buttons, pager, central taskbar, Clipboard applet, and digital clock. The panel is viewport-anchored; the taskbar is the only shrinkable flex region, while the launch, pager, Clipboard, and Clock clusters retain their intrinsic widths. The desktop shell's historical minimum dimensions are clamped to the current viewport so browser zoom and narrow windows cannot push the panel or its right cluster beyond the visible area.

Right-clicking only the unused background inside the Taskbar opens the compact taskbar context menu: `Configure Panel...`, a separator, and `Help`. `Configure Panel...` uses the existing user-origin `configure-panel` singleton, so its Most Used identity and guarded settings window are unchanged. `Help` cascades to the independent `about-kde-panel` singleton titled `About KDE Panel` and the historical `about-kde` singleton. Task buttons and every other Kicker control remain outside this hit target; the menu uses the shared KDE3 menu renderer and full-screen-safe upward/submenu positioning.

The rightmost segmented Clock is also the sole Calendar launcher. It remains the same-sized time/date presentation, but is keyboard-accessible as `Open Calendar`; Enter, Space, and pointer activation use its live DOM rectangle to create a Calendar window whose bottom-right meets the Clock's top-right, clamped to the current WorkArea. A repeated activation focuses the existing singleton without moving it; after close, the next activation recomputes the anchor. Calendar is intentionally absent from K Menu, QuickLaunch, Desktop icons, and Run Command aliases. It remains a real current-desktop taskbar application, but its definition is excluded from Most Used eligibility even for user-origin Clock launches. The Calendar client uses a normal vertical flex flow: header and footer retain compact intrinsic heights while the six-row date grid fills the remaining client area, so resize and maximize expand the grid without changing its typography or date semantics.

K Menu:

- `kicker/k-menu/menuModel.ts` defines the readonly, discriminated menu data model.
- Menu entries are `application`, `submenu`, `command`, `section`, or `separator`.
- Enabled application entries reference Application Registry app ids. Entries marked `newInstance` call `launchNewApplicationInstance(appId, intent?)`; ordinary entries call `launchApplication(appId, intent?)`.
- Most Used Applications is a current-page Application Runtime projection, not a menu-local or persisted list. A fresh Provider starts empty; explicit K Menu, Desktop, Desktop context, and QuickLaunch application launchers use the Runtime's `user` origin, while route/bootstrap/internal requests retain the default `system` origin. The Runtime records one user activation per stable application id even when the result only focuses/restores a singleton.
- Usage records contain only `{ appId, count, lastUsedSequence }` in Provider memory. The projection intersects the currently enabled Phase 5.88 K Menu applications, sorts count descending, then most-recent sequence descending, then code-point app id ascending, and shows at most three normal application rows. It has no localStorage, sessionStorage, VFS, metadata, URL, cookie, or visible count badge; a browser refresh mounts an empty usage state.
- The Start Menu-local model presents the fixed KDE 3.3 hierarchy. It maps Editors to KWrite, Internet to Konqueror, Settings to Configure the Panel, the direct Control Center rows to the existing Control Center, System to Konsole, Utilities to KCalc, Find Files to KFind, Help to historical About KDE, About die Nische to the project About surface, and Personal Files (Home) to the existing Konqueror Home intent.
- Disabled categories and unavailable command placeholders do not enter the Application Registry and have no executable side effects. The five implemented Actions are enabled: Bookmarks, Quick Browser, Run Command..., Lock Session, and Logout....
- K Menu Bookmarks projects the single Desktop-owned Konqueror bookmark tree recursively in its stored mixed order. Empty trees show a disabled `(No Bookmarks)` row and `Edit Bookmarks...`; leaf identity is the stable bookmark id. Activation resolves the live location through the shared typed Konqueror location-launch bridge, performs one user-origin Konqueror launch, and records that bookmark visit only after resolution is accepted.
- Quick Browser is a live VFS projection, not a second filesystem model. It exposes Home Directory (`/home/user`) and Root Directory (`/`). Directory submenus prepend Open in File Manager and Open in Terminal, then project ordered current children recursively; empty folders show a disabled `(Empty)` row. File and link actions reuse the same typed Konqueror location bridge, and the terminal action reuses Konsole's existing cwd intent.
- Run Command is one local Kicker dialog opened by either the menu command or Alt+F2. Its standard opaque KDE window shell owns the single focused Command field and Run / Cancel actions. It recognizes the registered browser-desktop application aliases, delegates VFS paths and accepted HTTPS locations to the shared Konqueror launch bridge, and otherwise runs only the existing in-browser shell command executor. It never invokes the host OS, does not persist history, closes after an accepted action, and keeps visible errors open for correction.
- Lock Session delegates to the existing Desktop Session authority. Logout opens its direct `End Session for "user"` confirmation; Logout delegates to the existing runtime/window reset boundary, while Cancel and Escape leave the session untouched. Persistent providers such as bookmarks and preferences remain outside that transient reset.
- `KMenu` owns local menu state with a small reducer; this state is not part of the Window Manager or Application Runtime.
- State tracks `isOpen`, `activeItemId`, and one `openSubmenuId`.
- Closing the root menu clears the active item and closes submenus.
- The K button toggles the menu and remains visually inset while open.
- The root menu renders above the Kicker in the panel popup layer.
- The Internet submenu is a real cascading submenu and currently launches Konqueror; Editors launches KWrite, System launches Konsole, Utilities launches KCalc, and Find Files launches KFind.
- Personal Files (Home) launches Konqueror with an application intent to open the VFS Home special location.
- Help launches the historical `about-kde` Runtime singleton, titled About KDE. The adjacent About die Nische entry launches the separate project About singleton.
- The direct K Menu Control Center row launches the KDE Control Center singleton. Settings -> Configure the Panel launches the separate singleton panel-settings application without duplicating Control Center.
- Control Center's initial page is an unselected Home page. Its local tree contains Appearance & Themes -> Background and Theme Manager, plus sibling Desktop leaves Behavior and Multiple Desktops; the Behavior presentation retains the existing `showDesktopIcons` preference identity even though the user-facing label is no longer Icons. Theme Manager presents the ordered `KDE_Classic` and `Redmond` single-selection list and edits only the local `themeId` draft. Multiple Desktops edits the local `desktopCount` draft only. All pages apply through the same guarded Defaults / Reset / Apply path, and runtime theme changes update the global semantic CSS authority without remounting windows or applications.
- Configure the Panel is a standalone application that reuses the existing panel preference draft, Apply/Reset/Defaults, persistence, and guarded-close semantics. It is a direct Settings menu row and remains absent from the Control Center page tree.

K Menu dismissal and keyboard navigation:

- Outside pointerdown listeners are registered only while the menu is open and are removed on close or unmount.
- Clicking inside the menu or on the K button is not treated as an outside click.
- Clicking desktop, windows, taskbar, quick launch, tray, or clock closes the menu without preventing the target click.
- Escape closes the menu and returns focus to the K button.
- ArrowUp and ArrowDown move between enabled items and skip separators and disabled entries.
- Home and End move to the first and last enabled item.
- Enter or Space launches application items or opens submenu items.
- ArrowRight opens a submenu from a submenu item and focuses its first enabled child.
- ArrowLeft closes the submenu and returns focus to the parent menu item.

K Menu, QuickLaunch, and Taskbar behavior:

- Explicit application launchers are call-site-specific. K Menu uses NEW for Konqueror, Konsole, KWrite, KCalc, KFind, and Home; Konsole K Menu and QuickLaunch do the same for Konsole. Konqueror Shell/Desktop and in-app new-window paths retain their existing NEW location intents, while Konqueror `Open with KWrite` creates a NEW KWrite for the exact stable file node.
- Ordinary application requests use the Runtime planner. They create a first window only when absent; otherwise they reuse the earliest matching window, restoring or focusing it across desktops when necessary. This is deliberately different from an explicit launcher and applies even when an application allows multiple windows.
- Taskbar and Task Group popup actions are exact `WindowId` operations only. Current-desktop rows toggle that window; off-desktop rows call `focusWindow(windowId)`. They never launch an application or resolve a target by caption.
- QuickLaunch open indicators are presentation-only current-desktop aggregates. They do not change the configured launcher action. Clicking an active taskbar button still minimizes that exact window.
- A non-minimizable task remains an exact task target, but an active click reasserts focus instead of minimizing it.
- KWrite File -> New, File -> Open, and Ctrl+Alt+N remain current-editor document replacement commands with their existing dirty guard; they are not top-level application launchers. Ctrl+N remains unclaimed for the browser boundary.

Taskbar data flow:

- `Taskbar` reads the registered window list from `WindowManagerProvider`.
- `selectTaskbarWindows` chooses the source before pure `groupTaskbarWindows` entries reach the existing two-row layout. The persisted `showTasksFromAllDesktops` preference defaults to `false`: false selects only `window.desktopId === currentDesktopId`, while true selects all open window records in stable creation order.
- `WindowId` is the sole cross-subsystem identity for a task member, focus request, desktop move, shell metadata, and application host. `appId`, caption rank, task position, and desktop-local ordinal are derived presentation or grouping data and never select a target window.
- Display captions are global collision presentation over all open windows, while task projection is desktop-scoped before `appId` grouping. A current-desktop task list can therefore correctly contain non-contiguous suffixes such as `KWrite` and `KWrite<3>`; toggling the all-desktops preference never renumbers a caption.
- Konqueror reports a small serializable `semanticIconId` through its existing per-`WindowId` shell metadata. Its pure location resolver reuses the VFS stable-node icon resolver: Start Page and file previews use Konqueror, canonical Home/Documents/Downloads/Music/Pictures/Videos and other existing special nodes reuse their established icons, ordinary directories use Folder, `trash:/` uses Trash, and `sysinfo:/` uses My Computer. Metadata contains no history, selection, or VFS node object and is removed on close/reset while remaining available through Lock.
- `getWindowShellIconId` is the shared Shell consumer: a valid exact-window `semanticIconId` wins; missing or invalid metadata falls back to the Application Registry icon and then the window's registered icon. `TaskButton`, grouped representative buttons, group popup rows, and `DesktopWindowLayer`'s `WindowFrame` icon prop use this same rule. WindowFrame has no location, caption, VFS, or previewer knowledge.
- Task surfaces first select that per-window semantic base icon, then apply the separate `getTaskWindowPresentation` running/minimized treatment. Titlebar icons intentionally use only the base icon. Desktop visibility, active state, captions, and app-level state do not choose or dim the icon. Unknown or unavailable Konqueror targets fall back to Konqueror. File-type semantic window icons remain deferred.
- One scoped window renders as an ordinary task. Two or more windows with the same `appId` render as one derived group entry at the earliest member's stable registration position; a group is not a `DesktopWindow` and has no synthetic window id.
- A group representative is the active member, otherwise the current desktop's last active member, otherwise the earliest current-desktop member, otherwise the earliest source member. Its final `window.title`, shell icon, and minimized/running presentation are all read from that same exact member, while popup rows retain their own final member captions and icons in creation order. Caption rank remains independent from representative selection.
- Task button and group entry order follow the stable registration order in the window array.
- Activating, minimizing, maximizing, restoring, or closing a window does not reorder remaining task buttons.
- With the default preference, `Taskbar` filters to the current desktop before grouping. With all-desktops enabled, same-app windows from every desktop share one `appId` group; the grouping key never becomes `appId + desktopId`.
- Current-desktop task rows delegate exact `window.id` actions to `toggleTaskbarWindow`. An off-desktop task row delegates to existing `focusWindow(window.id)`, which switches desktop and restores/activates that exact window. Neither path resolves by title or application-level launch lookup.
- Task icon presentation is derived per `WindowId`: the same window `state` produces the row's normal/minimized icon treatment and normal/dim text. Active selection is a separate concern and never infers minimized state.
- Konqueror's reusable SVG uses per-render gradient ids, so off-desktop mounted window frames cannot become a shared SVG paint server for Taskbar icons. Desktop visibility remains separate from minimized icon presentation.
- The group popup is Kicker-owned but logically remains in `Taskbar` while its open surface portals into `DesktopTransientPopupLayer`. It anchors its bottom edge to the actual `TaskGroupButton` DOMRect top, so a second-row task can overlap the first Kicker row. It clamps to the full screen, shares shell-popup mutual exclusion with K Menu and Klipper, closes on outside click, desktop switch, Show Desktop, Lock, and session teardown, and is not a body portal or WindowOwnedPopup.
- Taskbar remains a derived projection: changing its preference does not mutate WindowManager state, titles, VFS, or Konqueror UI state. Group popups close when the preference changes or the desktop switches.
- Moving a window changes only its desktop ownership and related active/session records. Current-desktop projection updates live from group to ordinary task or vice versa; all-desktops projection retains exactly one member per `WindowId`. Existing bounds, captions, application state, and component identity do not change.

Task button states:

- Active normal or maximized windows use an inset button state and `aria-pressed="true"`.
- Inactive normal or maximized windows use raised KDE 3 button styling and `aria-pressed="false"`.
- Minimized windows remain visible in the taskbar with a distinct minimized style and a restore-oriented accessible label.
- Closed windows are removed from the registry, so their task buttons disappear.

Pager:

- `VirtualDesktopPager` renders the fixed `DESKTOP_IDS` set as a compact `2 x 2` button grid.
- Each button calls `switchDesktop(desktopId)` through the Window Manager context.
- The current desktop uses `aria-pressed="true"` and an inset/current KDE 3 state.
- Arrow keys follow the `2 x 2` grid, with Home selecting desktop 1 and End selecting desktop 4.

Show Desktop:

- Quick Launch exposes Show Desktop as a window-manager action, not an application launch.
- `ShowDesktopSession` stores `windowIds` and `previouslyActiveWindowId`.
- `showDesktopSessionByDesktop` stores one independent session per virtual desktop.
- Entering Show Desktop records only non-minimized windows on the target desktop and clears active state on that desktop.
- Entering Show Desktop does not change window state, bounds, z-index, `restoreBounds`, `stateBeforeMinimize`, desktop id, task order, or mounted application components.
- Restoring Show Desktop clears that desktop's session and reactivates `previouslyActiveWindowId` if it still exists and is not minimized.
- If the previous active window is gone or minimized, restore selects the highest z-index visible window on that desktop.
- Normal Show Desktop restore does not raise windows or increment `nextZIndex`.
- Taskbar focus, application launch, cross-desktop singleton focus, and window restore/activate actions clear the target desktop session before focusing and may raise the target once through the existing focus rules.
- Closing or minimizing a session window removes it from that session; an empty session is cleared.
- Closing or minimizing the active window chooses the existing same-desktop visible fallback and issues that exact fallback a fresh application focus request. This preserves application-local focus handoff without a caption, representative, or app-wide focus lookup.

Future phases may add richer K menu entries, taskbar context menus, and panel configuration.

## Window Menu

Phase 2.6 adds a classic titlebar window menu opened from the application icon button on the left side of each titlebar.

State ownership:

- `window-menu/WindowMenuProvider` owns transient menu UI state, separate from `WindowManagerState`.
- State tracks `openWindowId`, `openSubmenuId`, `activeItemId`, and the anchor rectangle.
- Opening another window menu replaces the previous one; closing clears submenu, active item, and anchor state.
- The provider validates that the target window still exists, is on the current desktop, is not minimized, and is not hidden by Show Desktop.
- The menu closes when the target window is minimized, closed, moved off the current desktop, hidden by Show Desktop, when the virtual desktop changes, or when the browser resizes.
- K Menu and window menu are mutually exclusive through lightweight popup close events, not Window Manager state.

Rendering and layering:

- `WindowPopupLayer` is rendered inside the shell transient layer after Kicker.
- Window menu z-index is scoped inside `--kde-z-transient-popup`, so it stays above ordinary windows and the Kicker but below system overlays.
- The titlebar icon is a real `button`; pointerdown does not start titlebar drag and double-click does not toggle maximize.
- Clicking a non-active window icon calls existing `activateWindow` once before opening the menu.
- Menu position is calculated from the icon button rect relative to the desktop shell and clamped to the full screen area, so it may cover Kicker without leaving the viewport.

Menu commands:

- The shared system menu is exactly `To Desktop`, a separator, `Minimize`, `Maximize`, a separator, and `Close`.
- Minimize, Maximize, and Close delegate to existing Window Manager APIs. Maximize remains visible as `Maximize` and is disabled while the window is maximized or cannot be maximized; Minimize remains visible and is disabled for non-minimizable windows.
- Move and Resize are not menu entries. Normal titlebar dragging and capability-gated edge resizing remain owned by `WindowFrame`.
- `To Desktop` is a cascading submenu with one `menuitemradio` entry per configured desktop, preserving the existing `moveWindowToDesktop` reducer semantics.
- The titlebar application-icon click and titlebar contextmenu use this same menu model and action layer. Context menus on minimize, maximize, and close controls are suppressed without opening the system menu; a right-click on an inactive titlebar activates that window first.
- Escape and outside pointerdown close the menu; keyboard navigation skips separators and disabled entries.

To Desktop reducer rules:

- `moveWindowToDesktop(windowId, desktopId)` updates only the target window's `desktopId` plus related active, last-active, and Show Desktop session bookkeeping.
- It does not change window bounds, state, z-index, order, `restoreBounds`, `stateBeforeMinimize`, app id, window id, or mounted application component.
- Moving an active current-desktop window selects the highest z-index remaining visible window on the source desktop as fallback.
- If no source desktop window remains visible, the source desktop has no active window and `lastActiveWindowIdByDesktop[source]` becomes `null`.
- Moving a non-active window preserves the current active window and z-index values.
- Non-minimized windows moved to a target desktop without Show Desktop become that desktop's last-active record but are not made active until that desktop is current.
- Minimized moved windows remain minimized and do not overwrite a valid target last-active record.
- Moving into a desktop with an active Show Desktop session adds non-minimized moved windows to that target session without changing `previouslyActiveWindowId`.
- Moving a window out of a source Show Desktop session removes it from the source session; empty sessions are cleared.
- Moving a singleton application keeps the same app id and window id, so later launch requests focus it on its new desktop instead of creating another instance.

## Window Manager

Phase 1.4 extends the small Window Manager layer for registered desktop windows.

Current data flow:

- `Desktop` provides the initial registered window records.
- `WindowManagerProvider` owns reducer state and exposes actions through context.
- `WindowFrame` reads a `DesktopWindow` record and renders position, size, active state, and z-index from state.
- Window contents remain application components; they do not own placement or focus state.

Reducer/store responsibilities:

- Store registered windows, active state, bounds, z-index, state, and drag eligibility.
- Store `currentDesktopId`, `DesktopWindow.desktopId`, and `lastActiveWindowIdByDesktop`.
- Store `showDesktopSessionByDesktop`, keeping Show Desktop independent for each virtual desktop.
- Track `restoreBounds` separately from the current `bounds` for maximized windows.
- Track `stateBeforeMinimize` for minimized windows so taskbar restore can return to `normal` or `maximized`.
- Track `minimumWidth`, `minimumHeight`, and `isResizable` on each window record.
- Window registration can also declare `isMinimizable`, `isMaximizable`, and `alwaysOnTop`; omitted legacy values retain the historical minimizable/maximizable normal-window behavior.
- Activate one window at a time.
- Raise activated windows using a deterministic `nextZIndex`.
- Keep ordinary and always-on-top windows in generic WindowManager layers. Activation still controls focus in either layer, while every always-on-top window stays visually above normal application windows without competing with Kicker, transient popups, or system overlays.
- Minimize windows while keeping their bounds, z-index, and application content.
- Restore minimized windows to their pre-minimize state, activate them, and raise them once.
- Maximize normal windows to the current work area and save the previous normal bounds.
- Restore maximized windows from `restoreBounds`, constrained to the current work area.
- Close windows by removing them from the registry.
- Resize only normal, resizable windows.
- Toggle taskbar windows through a single reducer-controlled action.
- Reject all reducer and taskbar minimize requests for a window whose `isMinimizable` capability is false; titlebar and window-menu presentation derive from the same capability.
- Move only the target window.
- Re-clamp every window when the work area changes.
- Ignore unknown window ids without mutating state.
- Resize actions update only target bounds; they do not change state, active status, z-index, `restoreBounds`, `stateBeforeMinimize`, or window order.
- Move-to-desktop actions update only the target desktop assignment and related desktop bookkeeping; they do not switch the current desktop.

Virtual desktops:

- `DesktopId` is the fixed union `1 | 2 | 3 | 4`, with `DESKTOP_IDS = [1, 2, 3, 4]`.
- Initial windows belong to desktop 1 and `currentDesktopId` starts at 1.
- Each window belongs to exactly one desktop through `DesktopWindow.desktopId`.
- Desktop switching updates `currentDesktopId`, clears off-desktop active flags, and restores that desktop's last active visible window when available.
- If a desktop's last active record is missing, closed, or minimized, switching chooses the highest z-index visible window on that desktop.
- Empty desktops allow no active window.
- Switching desktops does not alter window bounds, state, z-index, order, `restoreBounds`, or `stateBeforeMinimize`.
- `lastActiveWindowIdByDesktop` is updated when a visible current-desktop window becomes active through window focus, taskbar restore/activation, launch, resize-start activation, maximize, or restore.
- Minimize and close fallback only consider visible windows on the same desktop as the target.
- Switching to a desktop with an active Show Desktop session does not restore windows and leaves that desktop without an active window.
- Switching away from a desktop with an active Show Desktop session preserves the session.

Focus and layering rules:

- Zero or one registered window may be active at a time.
- Only current-desktop, non-minimized windows may be active.
- Clicking a visible window area activates that window.
- Activating a non-top window raises it above the others.
- Clicking the already-active top window does not keep increasing z-index.
- Window z-index is local to `.desktop-window-layer`; it cannot raise a window above the Kicker.
- Active windows use the blue title bar tokens; inactive windows use the gray title bar tokens.
- Minimizing the active window activates the remaining visible window on the same desktop with the highest z-index.
- If no visible windows remain, all windows are inactive.
- Minimizing an inactive window leaves the current active window unchanged.
- Restoring a minimized window returns it to `normal` or `maximized`, makes it active, and assigns the next highest z-index.
- Closing the active window activates the remaining visible window on the same desktop with the highest z-index.
- Closing an inactive window leaves the current active window and z-index values unchanged.

Window states:

- `normal`: the window uses its own bounds and can be dragged by the titlebar.
- `maximized`: the window bounds equal the work area. `restoreBounds` stores the previous normal bounds for later restore.
- `minimized`: the window remains registered and mounted, but hidden. `stateBeforeMinimize` records whether restore should return to `normal` or `maximized`.

Maximize and restore:

- Maximized bounds are generated by `getMaximizedBounds(workArea)`.
- The maximized frame starts at the work area origin and ends at the Kicker top edge.
- Browser resize updates maximized window bounds to the latest work area.
- `restoreBounds` is not overwritten with maximized dimensions; restore returns the saved normal bounds, subject only to the current viewport recovery-position contract.
- After manual resize, maximizing stores the latest resized normal bounds in `restoreBounds`.
- Maximized windows cannot be dragged. Dragging from maximized to restored is intentionally not implemented.

Resize:

- `ResizeDirection` is the fixed union `n | ne | e | se | s | sw | w | nw`.
- `ResizeHandles` renders eight transparent pointer hit areas on normal resizable window roots.
- Resize uses Pointer Events and `setPointerCapture`; no document-level persistent listeners or third-party resize library are used.
- Resize and drag sessions are mutually exclusive. Starting resize stops pointerdown propagation so the titlebar drag handler cannot start.
- Pointer moves are coalesced with `requestAnimationFrame`; each frame commits only the latest pending bounds.
- Geometry is calculated by `resizeNormalWindowBounds`, a DOM-free pure function based on the original bounds, current pointer delta, and `ScreenArea`. It is distinct from the fixed-size titlebar move helper.
- East and south resizing may extend beyond the screen and behind Kicker; west resizing may extend left of screen while retaining the shared titlebar recovery strip, and north resizing stops at the screen top.
- West and north resizing keep the original opposite edge anchored by deriving size from the initial right or bottom edge. Corner directions compose those rules from the same initial bounds, avoiding coordinate drift.
- Declared application minimum sizes remain hard lower bounds. Normal windows may be wider or taller than the viewport; viewport changes correct only unrecoverable `x`/`y` positions and never shrink those normal dimensions.
- Minimized and maximized windows do not render resize handles and ignore resize actions.
- Minimize, maximize, restore, close, and unmount clean active drag or resize sessions, release pointer capture when available, cancel pending animation frames, and restore text selection.

Window visibility:

- Minimized windows remain in the window registry and keep the same React key.
- Off-desktop windows remain in the window registry and keep the same React key.
- `DesktopWindowLayer` renders all registered windows; it does not filter by desktop, so application component state is preserved while switching desktops.
- `WindowFrame` remains mounted but uses `hidden` while minimized or off-desktop.
- Hidden minimized and off-desktop windows are not visible, do not receive pointer events, and are not treated as visible active windows by assistive technology.
- Show Desktop hidden windows also remain in the registry and keep the same React key.
- Minimized state, desktop visibility, and Show Desktop visibility are separate: `state === "minimized"` records taskbar/window state, `desktopId !== currentDesktopId` records off-desktop visibility, and `showDesktopSessionByDesktop[desktopId]` records temporary desktop reveal state.
- The window root has explicit `display: flex` in the base KDE frame style, so hidden visibility also uses root classes and a dedicated `.window-frame[hidden], .window-frame.is-minimized, .window-frame.is-off-desktop, .window-frame.is-show-desktop-hidden { display: none; }` rule.
- The minimized/off-desktop/show-desktop class and `hidden` attribute must be applied to the absolute-positioned window root, not to the titlebar or application content.
- `display: none` removes the hidden frame from painting and hit testing while preserving the mounted React component instance.
- Closing differs from minimizing: close removes the window record, unmounts the frame and application component, and removes the task button. Refreshing the page returns to the same clean, empty-window desktop as first boot; applications open only through an explicit launcher action.

Workspace definition:

- The work area is the browser viewport minus the bottom Kicker panel.
- Runtime code reads the CSS panel and titlebar sizing tokens instead of hardcoding the panel height in TypeScript.
- Window bounds are clamped so normal windows remain inside the work area.
- If a window is larger than the work area, the title bar remains visible and usable.
- Maximized windows bypass normal clamping and use the exact work area bounds.

Not yet implemented:

- Window snapping.
- "Show on all desktops".
- Show Desktop animation or preview thumbnails.
- Always on Top.
- Keyboard Move or Resize mode from the window menu.
- Keyboard-driven resize.
- Persistent window size or position storage.
- Keyboard window switching or Alt+Tab.
- Window animations.

## Application Runtime

Phase 2.1 introduces a small application runtime above the Window Manager.

Application Registry:

- `applicationRegistry` stores immutable application definitions.
- Each definition includes `appId`, display name, default window title, window icon id, optional `instancePolicy`, preferred default bounds, minimum size, resize and maximize capabilities, optional initial sizing policy, and a render entry. `appId` is registry/component metadata; `DesktopWindow.id` is the unique mounted window-instance identity. Omitted `isMaximizable` remains true for legacy definitions and windows.
- Omitted instance policy defaults to `singleton`. Konqueror, KFind, KWrite, Konsole, and KCalc use their intended `multiple` policies; the About windows, KDE Control Center, and Configure the Panel remain singleton. `about-kde` is the historical About KDE target shared by application Help menus, while `about-die-nische` is the separate project About target; `about-konqueror`, `about-kwrite`, `about-konsole`, and `about-kcalc` are independent application-specific singletons. The existing first-window ids remain compatible as `app:<appId>`, while later session-only instances use deterministic `app:<appId>::<serial>` ids. A separate instance id is unnecessary because `window.id` already supplies it.
- Current registered applications include `konqueror`, `kfind`, `kwrite`, `konsole`, `kcalc`, historical `about-kde`, project `about-die-nische`, `about-konqueror`, `about-kwrite`, `about-konsole`, `about-kcalc`, `kcontrol`, and `configure-panel`.
- `ApplicationAbout` remains the shared generic About presentation, while `ProjectAbout` owns the die Nische Overview/Legal/Licenses surface and the historical `about-kde` presentation contains only KDE 3 context. Konqueror, KWrite, Konsole, and KCalc Help menus launch their application-specific singleton plus historical `about-kde` through the existing Application Launcher. About windows are ordinary independent Runtime windows; source applications retain no inline About state, modal layer, or source-window interaction lock.
- Unknown app ids return `undefined` and are rendered by `ApplicationHost` as a controlled unknown application message.

Window creation:

- `createApplicationWindow` converts an `ApplicationDefinition` into a `DesktopWindow`.
- First application instances use deterministic ids such as `app:konqueror`; a per-application monotonic Runtime serial reserves later ids without randomness, timestamps, browser storage, or reuse after close in the same session.
- Preferred dimensions are copied from the definition so runtime window changes cannot mutate the registry; registry `x/y` are not an application placement authority.
- `resolveApplicationInitialBounds` applies creation-time sizing policy before a new window opens, then centers that final size in the current `WorkArea`. Konqueror uses a `600px` preferred height capped by `maximumWorkAreaHeightRatio: 0.72`; About has no ratio policy and keeps its preferred size.
- Height ratio resolution uses `floor(workArea.height * ratio)`, then clamps against preferred height, work area height, and an effective minimum of `min(minimumHeight, workArea.height)` with a safe `1px` lower bound.
- Created windows start in `normal` state without `restoreBounds` or `stateBeforeMinimize`.
- The Window Manager clamps bounds when the window is opened into the current work area.

ApplicationHost:

- `Desktop` maps registered windows to `WindowFrame`.
- `ApplicationHost` receives the current window record, uses `window.appId` for the registry lookup, and uses `window.id` for launch requests, close guards, and title updates. `DesktopWindowLayer` keys each mounted frame/host by `window.id`, so future same-app React components retain independent local state.
- Adding a new registered application should not require adding app-specific render branches to `Desktop`.

Launch behavior:

- `ApplicationRuntimeProvider` exposes `launchApplication(appId, options?)`.
- It also exposes `launchNewApplicationInstance(appId, options?)`. A multiple-policy definition receives a deterministic current-desktop window and has its initial intent stored by that new window id before mount. A singleton definition ignores this disposition and reuses its existing window.
- Standard `launchApplication` retains existing-or-new behavior. For a multiple-policy definition it reuses the oldest matching instance; only the explicit new-instance API allocates another one. Restore and cross-desktop focus remain exact-window Runtime actions.
- `options.intent` is wrapped in an `ApplicationLaunchRequest` envelope with a deterministic monotonically increasing `requestId`.
- The Runtime stores the latest request and pending close guard by window id and passes them through `ApplicationHost`; it does not import VFS, parse paths, or understand Konqueror-specific intents. Repeated equivalent intents still receive new per-window request ids.
- Applications validate the `unknown` intent at their own boundary. Konqueror accepts typed special-location, directory, file, sysinfo, and Start Page intents; file and directory intents contain only stable VFS node ids plus the optional current previewer id. Konsole also accepts a typed `open-working-directory` intent containing one canonical absolute VFS path; it is consumed only by that exact new window's initial state.
- Unknown applications are no-ops and return `unknown-application`.
- Launching an unopened application creates a window through the registry, appends it to the window list, activates it, and gives it the highest z-index.
- Opening a new window with an intent stores the initial launch request before the application is rendered, so Konqueror can start directly in Home or Trash without a visible intermediate navigation.
- Explicit NEW windows are assigned to the current desktop at launch time; an ordinary request may instead focus the selected existing window on another desktop.
- Launching an already-open singleton does not create duplicates.
- Launching an already-open singleton with an intent updates that window's latest launch request without remounting the application component.
- Launching a visible inactive singleton activates and raises it.
- Launching a minimized singleton restores it through the existing Window Manager restore rules.
- Launching the already-active top singleton is stable and does not grow z-index.
- Launching a singleton that already exists on another desktop does not move the window and does not create a duplicate. The Window Manager uses `focusWindow` to switch to the target desktop, restore the window if needed, activate it, and raise it once.
- If a singleton window was moved to another desktop through the window menu, later launch requests use that new `desktopId`.
- Application launch and cross-desktop singleton focus clear the target desktop's Show Desktop session before showing and activating the target window.
- Creation-time sizing applies only to first load and relaunch after close. Launching an already-open app activates or restores the existing window and does not reset user-resized bounds.
- Konqueror's registry default launch intent is `open-konqueror-start`. Its Shell/Desktop launchers explicitly request a new instance, while its in-window navigation remains component-local. Other applications still have no implicit launch intent.
- Closing a window prunes only that instance's stored launch request and close guard. Instance serials, intents, and guards are volatile Runtime session state: End Current Session clears them, while Lock preserves them.

Quick launch and taskbar:

- QuickLaunch keeps each item's configured application-level action: Home and Konqueror preserve their NEW Konqueror intents, and Konsole creates NEW terminals. Historical About KDE remains available from Help routes and the project About is available from the K Menu; neither is duplicated as a Quick Launch button. Their open indicators are not planner inputs.
- Taskbar buttons use exact window-level toggle behavior on the current desktop, and targeted `focusWindow(window.id)` behavior for an off-desktop task when the all-desktops preference exposes it.
- Individual Taskbar actions retain `window.id` identity and icon metadata is resolved from exact per-window semantic metadata with the registered application icon as fallback. The Taskbar presentation may derive one current-desktop group entry for two or more same-app windows, but group membership does not alter WindowManager identity, ordering, captions, or lifecycle.
- This means clicking the active taskbar button minimizes that window, while an explicit QuickLaunch entry still follows its configured NEW/reuse action.
- Kicker/K Menu Konqueror opens a new blank-address Start Page instance. Kicker/K Menu Home opens a new `/home/user` instance. Desktop Trash and My Computer retain their new `trash:/` and `sysinfo:/` instances. Taskbar activation remains a window-level action and never creates an instance.
- Ordinary Konsole launchers and Session -> New Window launch `konsole` with no intent and retain the Home default. Konqueror's directory-only Open Terminal Here action is the one explicit launcher that supplies a Konsole working-directory intent.
- Help launches historical `about-kde`. Konqueror also launches an independent `about-konqueror` Runtime singleton from Help; both use ordinary modeless WindowFrame and Taskbar lifecycle and can coexist. The project About uses its separate `about-die-nische` singleton and does not share the historical identity.

Initial applications:

- Initial windows are generated from `initialApplicationIds` through the same application definition and window creation path used for later launches.
- Browser boot creates no application windows. Explicit first launch and close-then-relaunch both use the application initial-bounds resolver without mount effects.
- Initialization is pure and does not use mount effects, so React Strict Mode does not launch duplicate windows.
- Window-array insertion order remains stable creation order; raising z-index never rewrites it.

Phase 5.19 foundation:

- Runtime and Window Manager can represent independent same-app windows with isolated title, bounds, desktop, focus request, close guard, launch intent, Taskbar action, Show Desktop, and close lifecycle state.
- The runtime foundation itself has no application-specific multi-window command surface.

Phase 5.20 Konqueror multi-window UX:

- Shell/Desktop Konqueror launchers use `launchNewApplicationInstance`: Kicker/K Menu Konqueror starts `about:konqueror` with blank address presentation and Location focus; Kicker/K Menu Home starts `/home/user`; My Computer starts `sysinfo:/`; Trash starts `trash:/`. Each has fresh history and starts on the current virtual desktop.
- Start Page links, toolbar and Go navigation, Location submissions, Back/Forward, default directory/file activation, and Preview switching remain current-window behavior. KFind result activation is intentionally separate: it resolves the saved stable VFS node id against current state and requests a new Konqueror instance for either directory or file targets.
- File/Location New Window preserves an independent window launch from the active target. Internal tabs are exact-window session state: the implicit first tab remains hidden, New Tab creates an active `about:blank` stable `TabId`, Open in New Tab adds the clicked resource target, and the bar disappears when closing back to one session. Duplicate Current Tab copies only the current target into a fresh history root; it does not clone history, selection, or tree expansion. Tabs have no rename, reordering, browser integration, or persistence.
- Konqueror React state is instance-local by the `window.id` host key. Each window owns a nonpersistent `KonquerorWindowTabs` value with stable monotonic `TabId` sessions and an `activeTabId`; its initial tab is logical but visually implicit. Each `TabSession` owns navigation/history, Location draft/error, stable selection/range anchor, and Tree expansion. View mode, sort, and resource zoom retain their existing exact-window presentation/preference authority, while embedded/external zoom and load lifecycle retain their existing exact-window presentation scope. VFS remains shared and stable node ids therefore keep previews live through cross-window and cross-tab Save, Rename, Move, Trash, Restore, and permanent deletion.
- The file-operation clipboard is a small session-owned `KonquerorClipboardProvider`, shared by Konqueror instances and reset with End Current Session. It remains distinct from Klipper's text/URI history; Copy/Cut in one window can Paste in another while the existing URI mirror behavior remains intact.
- Initial top-level application placement is generic: a fresh `(DesktopId, ApplicationId)` group resolves its final initial size, centers it in the current `WorkArea`, then uses that centered bounds as cascade slot `0`. Later windows keep a monotonic Runtime cascade serial, but map it to a derived visual slot using the current Work Area, that resolved bounds, and the existing `24px` diagonal step as a right/bottom edge safety margin. The capacity includes slot `0`, is at least one, accepts equality with the safe boundary, and wraps before initial-bounds clamping could stack candidates at the right edge or Kicker. `WorkArea.bottom` is the Kicker boundary; Screen Area is not used. Small windows or larger viewports therefore admit more visual slots, while large windows or constrained viewports can fall back to capacity one and reuse the centered origin. This is not arbitrary-window collision avoidance, tiling, or a second cascade track. The volatile cascade key is exactly `DesktopId + ApplicationId`, not caption rank, z-index, task projection, or WindowId serial. Slots remain monotonic while that group has any open window, including minimized windows; closing or moving out its final member clears the key, so the next new window starts centered at slot `0`. Moving into a target desktop seeds that target group for later new windows without repositioning the moved window. Different applications intentionally have independent centered origins and can overlap. Lock preserves this runtime-only state; End Session clears all keys. Existing windows are never recentered on activation, restore, desktop switch, or viewport expansion; a resize only affects capacity for future windows.
- Applications report an unsuffixed `baseTitle`; Window Manager derives the user-visible `title` as a display caption. The generic pure resolver groups every open window by exact `(appId, baseTitle)`, then ranks in stable `state.windows` creation order. It deliberately ignores focus, z-index, desktop, minimization, and taskbar projection. A collision renders `Caption`, `Caption<2>`, `Caption<3>` with no space before `<n>`; close, live base-caption changes, navigation, and Rename reindex without gaps. The suffix is never part of application semantics, location, history, VFS data, or `WindowId`.

### Multi-Instance Window Runtime

- `ApplicationId` identifies a definition; `WindowId` identifies one mounted top-level runtime window. `DesktopId` owns that window, `baseTitle` is application semantic data, and `title` is the shell-derived global caption. Task groups use `appId`, caption collisions use `(appId, baseTitle)`, and cascade serials use `(DesktopId, appId)`; none substitutes for another identity.
- Konqueror, KFind, KWrite, Konsole, and KCalc are intended multiple-instance applications. Explicit user launchers create a new current-desktop window, ordinary `launchApplication` requests reuse the planner-selected existing window, and Taskbar actions activate, restore, or minimize one exact existing `WindowId`. About and KDE Control Center remain singleton.
- Application session state belongs to the mounted window component: navigation/editor/search/terminal/calculator state never crosses WindowIds. The normalized VFS, file-operation clipboard, preferences, and shell Window Manager state remain intentionally shared. Stable `WindowId` React keys preserve those sessions through caption reindexing, task projection changes, and desktop moves.
- Every active transition issues an exact `focusRequestId`; application-local focus surfaces consume only their own request. Cross-desktop focus switches desktop, restores when needed, activates the target, and hands it focus. Show Desktop is not minimized, Lock preserves the runtime beneath its overlay, and End Session clears windows, task source, focus and cascade Runtime state without restoring an application session.

### Window-Owned Popup Layers

- Desktop-owned menus remain in `DesktopPopupLayer`; the titlebar Window Menu remains in the existing `WindowPopupLayer`. They are not a shared global application-context-menu host.
- Each `DesktopWindow` mounts a `WindowOwnedPopupLayer` that carries the owner `window.id`, shares that window's stacking order, defaults to `pointer-events: none`, and gives only its popup children pointer interaction. The target is physically portaled into `DesktopTransientPopupLayer`, while normal application client content remains inside the clipped `WindowFrame`.
- Application popups use a React portal only to this owner-scoped shell target, never to `document.body`. The target is hidden with its owner on minimize, desktop changes, or Show Desktop, remains above Kicker and below Lock/session overlays, and does not participate in window bounds or document layout.
- Konqueror context menus capture primitive browser `clientX` / `clientY` values at the source event, convert them through the owner popup layer's `DOMRect`, and clamp the result to the full screen area. The screen area, rather than Konqueror client or normal-window work-area bounds, also controls submenu left-flip and bottom placement.
- Context-menu open requests carry a local monotonic request id. The desktop and Konqueror menu surfaces mount hidden with pointer interaction disabled, measure their current DOM dimensions in a pre-paint layout effect, and become visible only when the resolved Screen Area-clamped position belongs to that same request. A later request invalidates the previous coordinates, so no default, raw, or stale position is painted; this does not change popup ownership, menu content, or geometry policy.
- Window frame interaction starts, minimize, maximize, close, and titlebar menu activation publish an owner-scoped popup dismissal generation. Konqueror consumes it locally without a global pointer monitor. Existing shell-popup dismissal continues to clear menus for Lock and End Session.
- A window-owned portal remains in its source React tree. `WindowFrame` therefore recognizes its own popup-layer DOM containment before publishing a dismissal generation, so a menu item's `pointerdown` cannot unmount that item before its command `click`. Outside targets still dismiss and retain their first-click behavior; popup ownership is always the specific `WindowId`.
- Kicker launcher presence and toggle pressed state are separate. Current-desktop aggregation selects the Konqueror/Home icon variant without making those launcher buttons persistently pressed. Konqueror is open when any current-desktop Konqueror window exists, including minimized or Show Desktop-hidden windows. Home is open when any current-desktop Konqueror reports the stable VFS Home directory through small per-window shell metadata; captions and launch source are not used. Metadata is removed with its window. Show Desktop alone retains toggle pressed semantics. The Taskbar's all-desktops preference does not affect QuickLaunch presence.

Lifecycle:

- Minimize keeps the window record and mounted application component.
- Close removes the window record, unmounts the application component, and removes the task button.
- Relaunch after close creates a new application component instance using the default application window definition.

Not yet implemented:

- Full K menu customization.
- Run Command.
- Konqueror UI for Restore To, Save As, binary editing, multi-select, drag-and-drop, Undo, or context menus.

## Virtual File System

Phase 3.1 adds a browser-memory virtual file system core. Phase 3.2 makes Konqueror the first read-only VFS consumer. Phase 3.3 connects New Folder, New Text File, and Rename. Phase 3.4 adds basic UTF-8 text editing with Save and Discard Changes. Phase 3.5 extends the VFS data layer with Move, Copy, Trash, Restore, permanent delete, and Empty Trash semantics. Phase 3.6 exposes single-item Copy, Cut, Paste, Move to Trash, and read-only Trash browsing in Konqueror. Phase 3.7 connects Trash Restore, Delete Permanently, Empty Trash, Trash metadata columns, and desktop Home/Trash launch intents.

Scope and ownership:

- `src/vfs` owns the VFS data model, path utilities, queries, mutations, invariants, React context, provider, and hook.
- VFS is independent from Window Manager, Application Runtime, Kicker, and virtual desktops.
- `VfsProvider` wraps the application root above the desktop/window/application providers so future apps can share one VFS instance.
- Closing and reopening Konqueror does not reset VFS state because the provider is outside application windows.
- Refreshing the page recreates the initial in-memory tree.
- No `localStorage`, IndexedDB, browser File System Access API, upload/download, or real disk access is used.

Data model:

- `VfsNode` is a discriminated union of directories, files, and links. A file has one typed `content` payload: `{ kind: "text", text }` for editable UTF-8 text or `{ kind: "asset-url", url }` for a static build asset. File identity, MIME type, timestamps, and `size` remain node metadata rather than content payload fields.
- Nodes are stored in `VfsState.nodesById`; directories store ordered `childIds` rather than nested child objects.
- Each node has a stable immutable id, name, parent id, `createdAt`, and `modifiedAt`.
- Root is a directory with `parentId: null` and an empty name.
- Paths are not stored on nodes. Full paths are derived from parent links.
- Text files store UTF-8 content, MIME type, encoding, and byte `size`.
- `size` is UTF-8 byte length, not JavaScript string length.
- `revision` increments only after successful mutations.
- `nextNodeSequence` generates deterministic ids such as `vfs-node-0010`.
- `trashEntriesByNodeId` stores Trash metadata separately from ordinary `VfsNode` records.
- A `VfsTrashEntry` records the trashed subtree root id, original parent id, original name, and injected `trashedAt` timestamp.

Initial tree:

- `/`
- `/home/user/Desktop`
- `/home/user/Documents/Welcome.md`
- `/home/user/Documents/Notes.txt`
- `/home/user/Downloads`
- `/home/user/Music`
- `/home/user/Pictures`
- `/home/user/Videos`
- `/home/user/.local/share/Trash/files`
- `/media/cdrom`
- `/media/floppy`

Repository content baseline:

- `content/home/user/**` is the repository-owned baseline source for future VFS content. Its physical path maps directly to `/home/user/**`; `content` never appears in a virtual path.
- `npm run generate:vfs-content` recursively scans that tree and writes the ignored intermediate module `src/generated/vfsContentManifest.generated.ts`. The generated module is not source of truth and is regenerated before `dev`, `build`, `test`, `test:run`, `lint`, and `typecheck`.
- Repository content supports UTF-8 `.txt`, `.md`, `.markdown`, `.html`, and `.htm` text, plus `.png`, `.jpg`, `.jpeg`, `.gif`, `.webp`, and `.bmp` images, `.mp3`, `.ogg`, `.oga`, and `.wav` audio, and `.mp4`, `.webm`, and `.ogv` video with case-insensitive MIME matching. Text is embedded as `{ kind: "text" }`; images, audio, and video are generated as deterministic Vite `?url&no-inline` imports and become `{ kind: "asset-url" }` at runtime. Asset `size` is the original source binary byte count, never the URL length. Audio and video have no publication metadata, playback application, playlist, or Amarok integration; Konqueror's Media previewer consumes only their typed VFS asset URLs. `.gitkeep`, `.DS_Store`, `Thumbs.db`, and `.kde3-*` housekeeping entries are ignored, while ordinary supported hidden files are not globally excluded. The one exception is a directory-local `.kde3-meta.json` sidecar, consumed by the generator and never emitted as a VFS entry.
- `.kde3-meta.json` is strict immediate-child metadata. v1 remains readable with optional `id`, `modified`, and `order`; v2 adds optional `created`; v3 adds optional plain-text `displayName`; v4 adds optional `publication` for supported repository text files only; v5 adds optional authored `publication.slug`; v6 adds optional authored `publication.aliases`. v1/v2 reject `displayName`; v1/v2/v3 reject `publication`; v4 rejects `slug`; v1-v5 reject `aliases`; entry fields remain closed to `id`, `created`, `modified`, `order`, `displayName`, and `publication`. A publication is explicit `draft` or `published` intent: published entries require canonical UTC `publishedAt`, and v5/v6 published entries require a slug; drafts forbid `publishedAt` and may reserve a slug plus v6 aliases. Every v6 alias requires that canonical slug, is a non-empty ordered exact-unique array using the same lowercase ASCII `^[a-z0-9]+(?:-[a-z0-9]+)*$` grammar, and cannot repeat the current slug. Canonical slugs and aliases share one repository-wide namespace across v5/v6 publications and drafts, without trimming, normalization, or automatic slug-history capture. Optional plain-text `summary` plus ordered, exact-unique plain-text `tags` are validated without case folding or sorting. Directories, platform mounts, images, and unmanaged runtime files cannot receive publication metadata. Entry keys must be immediate visible child names, so traversal, nested paths, stale children, ignored bookkeeping files, unknown versions, and typos fail generation with a repository-relative error. Sidecars remain Node-side authoring input; raw JSON never enters the browser bundle or VFS.
- The stable current `.kde3-meta.json` wire format omits the top-level `version` field. Missing `version` is permanently pinned to historical v6 semantics, while explicit v6 remains accepted as an equivalent representation. Explicit v1-v5 retain their historical schemas; missing `version` never floats with a future latest version. Current stable writers omit `version`, and the read-only generator/build path never rewrites sidecars.
- VFS `name` remains the canonical filename/path component. `displayName` is an optional presentation-only field: it is plain text, may be duplicated, falls back to `name`, and never changes IDs, resolution, Shell paths, relative resources, Rename inputs, or runtime file operations. Konqueror, KWrite document/recent presentation, and KFind result labels consume the shared fallback helper; Name sorting and KFind matching remain canonical. Publication metadata is a separate, typed file-only field and has no filesystem visibility, sorting, shell, KWrite, KFind, or Konqueror effect outside publishing surfaces. The pure `buildPublishedContentCatalog(state)` selector derives publishing data from the current live Home VFS tree rather than storing a second state: each projection contains only `nodeId`, canonical path/name, title, optional current slug, copied ordered aliases, `publishedAt`, optional summary, and copied ordered tags, never file body content. It includes published text files only, excludes drafts/unmanaged files, special non-Home trees, and Trash descendants, and sorts by `publishedAt` descending, canonical path ascending, then node ID ascending using code-point comparison. Rename/move update its path projection; Trash removes an entry while preserving publication for Restore; Copy and Save As stay excluded because they create identities without publication. A pure route module formats and parses only `#/blog/<route-token>` and resolves that token against the current catalog as either a canonical slug or a direct historical alias; impossible synthetic duplicate matches resolve to nothing. Alias resolution derives the entry's current slug, replaces the current hash with `history.replaceState`, then launches the same nodeId-based Reader once. It neither pushes history nor assigns `location.hash`, so alias canonicalization does not make a Back-loop. The Desktop-level controller owns initial-hash and history-event launches, and hands a resolved stable node ID to a normal new Reader instance. It neither traverses VFS nor stores URL/title/body snapshots, and unrelated fragments remain untouched. The code-owned singleton Blog renders the selector order directly: slugged publications are native canonical hash anchors that update history then launch the multiple-instance Reader once, while v4 entries retain the nodeId-only button fallback; aliases are never listed. Each Reader re-derives its current catalog entry, canonical VFS source path, and text body from live VFS state. Published and live nodes are readable; Trash, draft/unpublished metadata, or deletion yields an unavailable view without stale publication body, while Restore or re-publication can recover it. Reader titles are catalog presentation titles, not paths; canonical paths remain source information; a permalink row exists only for a live current slug and never displays aliases. Its text body reuses Konqueror's safe Markdown parser, safe HTML parser/sanitizer, document-relative VFS resolver, and VFS asset URL boundary. Internal body links use a normal Konqueror open intent and safe HTTPS links use the existing external-web target. There is no pathname routing, slug generation, automatic alias history, HTTP/server redirect, alias editor, or Reader history. Blog is a code-owned Desktop launcher alongside Trash and My Computer, while Article Reader has no Desktop launcher. Platform mounts remain code-owned and root metadata cannot set their display labels.
- `getPublishedArticleNeighbors(catalog, currentNodeId)` is a pure positional projection over that same live catalog: `previous` is `catalog[index - 1]`, `next` is `catalog[index + 1]`, with no local sort, traversal, wrap-around, title lookup, or persisted neighbor state. Article Reader recomputes these controls whenever its live catalog changes, so Trash, Restore, draft/republish, and publication-order updates immediately remove or restore neighbors. The footer presents catalog titles but uses stable target node IDs. Slugged v5/v6 neighbors are canonical native `#/blog/<slug>` anchors, never aliases, and reuse Blog's accepted unmodified-click `pushState` plus one Reader launch contract; modified activation remains native. Slugless v4 neighbors remain adjacent and use an ordinary nodeId-backed Reader launch without inventing a route. Each footer navigation action opens a new normal multi-instance Reader and leaves the originating Reader bound to its original node ID; same-window replacement, Reader history, wrap-around, related/filter-aware navigation, prefetching, and keyboard navigation are deferred.
- An optional explicit ID must match `vfs-content-` followed by a non-empty `[A-Za-z0-9._-]+` suffix and must be globally unique in the final baseline. It overrides the default path-derived SHA-256 ID; without it the path-derived default remains unchanged. Repository rename or move keeps an identity only when the author moves the sidecar entry to the new immediate parent/key and retains the explicit ID. Runtime VFS rename and move already preserve identity in memory and never write sidecars. Platform-owned `/home/user` mount directories retain their platform IDs; root sidecars may target them only with `created` and `modified` metadata.
- `created` and `modified` are independent optional strict UTC ISO instants in `YYYY-MM-DDTHH:mm:ss.sssZ` form. They map only to deterministic VFS `createdAt` and `modifiedAt`, respectively; omitted values retain the project epoch `2026-08-30T12:00:00.000Z`. The read-only generator never reads live filesystem timestamps or Git metadata. In development only, the Node timestamp reconciler observes supported regular-file bytes, captures birthtime then mtime then an authoring clock for a new `created`, and captures mtime then the clock for `modified` after a genuine SHA-256 byte change. A newly created sidecar is authored as v6 and written atomically before generation; an existing v1-v5 sidecar remains readable and is not bulk-upgraded by a read-only scan. A v6 deletion removes the complete stale immediate-child entry, including identity, display, timestamp, ordering, publication, and alias metadata, while keeping live siblings intact; older explicit entries retain their existing diagnostic behavior. Build, test, lint, typecheck, and browser runtime consume committed sidecars only. Directory `modifiedAt` is persisted logical repository-content activity: real add/change/delete/rename/move events update every affected repository ancestor in one reconciled timestamp, never derive from maximum remaining child time; deletion advances that history and automatic rollback is intentionally not performed. Root sidecars may provide `created`/`modified` for platform mounts but may not override their `id` or `order`. `order` is an optional safe integer (negative values are valid): ordered siblings come first in ascending order, ties use code-point lexical name order, then unordered siblings use that same lexical order. This determines raw generated `childIds`, including image previous/next traversal; it does not override Konqueror's explicit Name, Size, Type, or Modified sorting.
- The scanner emits deterministic POSIX paths, validated final IDs, original binary or UTF-8 byte sizes, sidecar-derived ordering, and deterministic timestamps. It never follows symlinks, embeds base64, fetches URLs, includes a machine path or build timestamp in browser output, and fails on unsupported files, symlinks, malformed metadata, duplicate identities, or unsafe paths.
- The initial-state adapter merges that manifest after the existing platform seed. `/home/user` and its Desktop, Documents, Downloads, Music, Pictures, and Videos directories are mount points: their stable platform IDs and metadata are reused, while generated descendants append in manifest order. Any other collision with an existing seed node fails rather than overwriting or duplicating it. Videos is an ordinary empty repository-backed directory by default, with no production video fixture or media-library behavior.
- Repository content is only an initial baseline. Konqueror, KWrite, KFind, and Konsole continue to consume the existing VFS APIs, and browser Rename, Move, Delete, and Save mutate only the in-memory VFS. Refresh recreates the repository baseline; no operation writes to the Git working tree or browser persistence.
- In Vite development mode only, `npm run dev` performs timestamp reconciliation before its initial manifest generation. The plugin then observes add, change, unlink, add-directory, and unlink-directory events beneath `content/home/user`, debounces and serializes `reconcile -> generate -> full reload`, and suppresses its own atomic sidecar watcher events. v6 entries are fully removed on deletion; v1-v5 retain the established automatic-only cleanup, leaving explicit stale authoring metadata available for the generator diagnostic. A successful generation deliberately recreates the initial VFS and discards browser-session mutations. A reconciliation or generation error leaves the last valid generated module and current page in place, logs a repository-relative error in the development terminal, and later valid events retry normally. The watcher is build-tool code, not browser runtime code; production builds, tests, lint, and typecheck remain one-shot read-only generation workflows.
- Current repository-owned baseline files, including Documents text/HTML/Markdown content and the current `Pictures/*.png` assets, use the same deterministic generator and merge path. Text becomes UTF-8 VFS content while images and supported audio/video become static Vite asset URLs with original binary sizes. The existing Music mount is reused; no production video fixture or new VFS root is introduced. Runtime Save, Rename, Move, Delete, and Copy still operate only on in-memory VFS state; a refresh recreates the committed baseline and never writes back to `content/` or metadata sidecars.
- The former hardcoded `Pictures/A.png` data-URL seed has no compatibility alias. The Pictures baseline is entirely repository-content generated; image previews receive Vite asset URLs rather than base64 image payloads in generated JavaScript.

Special locations:

- `home` points to `/home/user`; `videos` points to the standard `/home/user/Videos` mount.
- `desktopDirectory`, `documents`, `downloads`, `music`, and `pictures` point to user directories.
- `trash`, `cdrom`, and `floppy` point to directories.
- `trash` points to the canonical XDG-style virtual backend `/home/user/.local/share/Trash/files`; there is no `/trash` VFS root.
- Trash is a normal VFS directory for path traversal, plus metadata-backed semantics for entries moved there through the VFS Trash mutation. `.local` remains accessible through explicit VFS and Shell paths but is hidden from ordinary Konqueror Home listings; no hidden-files setting is added.

Path rules:

- Paths use POSIX separators and are case-sensitive.
- Multiple `/` characters collapse to one.
- `.` is removed and `..` walks to the parent, clamped at root.
- Relative paths resolve against an absolute cwd.
- Empty paths resolve to cwd.
- Windows drive paths and backslashes are invalid.
- `~`, environment variables, and URL decoding are not supported.

API shape:

- Query functions return `VfsResult<T>` and never mutate state.
- Mutation functions return `VfsMutationResult<T>` with the original state on failure and a new immutable state on success.
- Expected errors use result objects with codes such as `INVALID_PATH`, `INVALID_NAME`, `NOT_FOUND`, `NOT_DIRECTORY`, `IS_DIRECTORY`, `ALREADY_EXISTS`, `ROOT_OPERATION_FORBIDDEN`, `INVALID_DESTINATION`, `SPECIAL_LOCATION_OPERATION_FORBIDDEN`, `ALREADY_IN_TRASH`, `NOT_IN_TRASH`, and `RESTORE_TARGET_UNAVAILABLE`.
- Query APIs include path resolution, id lookup, reverse path lookup, directory listing, text file reading, and Trash entry listing.
- Mutation APIs currently include create directory, create text file, write text file, rename node, move node, copy node, move node to Trash, restore from Trash, permanently delete a Trash entry, and empty Trash.
- Binary files, symlinks, permissions, mounts, persistent storage, and UI-level undo are intentionally not implemented.

Relocation and copy:

- Move changes a node's parent directory and can optionally rename it in the same mutation.
- Same-directory move without a new name, or with the same name, is a successful no-op.
- Same-directory move with a different name follows the existing Rename semantics and preserves child order.
- Move preserves node ids, subtree ids, content, file size, created time, and child order. It updates source parent, destination parent, and moved node `modifiedAt`.
- Copy recursively duplicates a file or directory subtree into a destination directory. New copy identities retain content and presentation metadata but clear publication metadata, while rename, move, Trash, Restore, and editing the same file identity preserve it.
- Copy allocates new deterministic ids in depth-first order: copied root first, then children in source `childIds` order.
- Copied nodes receive injected `createdAt` and `modifiedAt`; copied text content, MIME, encoding, and UTF-8 size are preserved.
- Regular Move and Copy cannot target Trash or any directory inside the Trash subtree. Trash entries must be created by the dedicated move-to-trash mutation so metadata is present.

Trash semantics:

- Protected locations cannot be moved, trashed, or permanently deleted: root, Home, Desktop, Documents, Downloads, Music, Pictures, Videos, Trash, CD-ROM, and Floppy.
- Moving to Trash removes the node from its original parent, appends it to the Trash directory, preserves the subtree ids, and creates one `VfsTrashEntry` for the top-level trashed subtree root.
- Trash direct child names remain unique. If a name is already present, deterministic names such as `Report (1).txt` and `Project (1)` are generated while `originalName` keeps the true source name.
- Restore uses the stable `originalParentId` and `originalName`. It fails if the original parent is missing, not a directory, inside Trash, or already contains the original name.
- Permanent delete only accepts a top-level Trash entry. It removes the full subtree and any related Trash metadata.
- Empty Trash deletes every direct Trash child and its descendants, clears Trash metadata, and preserves the Trash root node.

State invariants:

- `validateVfsState` checks root validity, parent-child consistency, duplicate children and names, reachability, parent cycles, special locations, file size consistency, next-id collisions, and Trash metadata consistency.
- Trash invariants ensure entry node ids exist, direct Trash children have metadata, non-direct Trash nodes do not have top-level entry metadata, original names are valid, and Trash root itself has no entry.
- An entry's original parent is not required to still exist or remain outside Trash; Restore performs that availability check at mutation time.
- Invariants are for tests and diagnostics; normal queries do not traverse the whole tree to validate every call.

React lifecycle:

- `VfsProvider` lazily calls `createInitialVfsState`.
- `useVfs` exposes state plus query and mutation commands.
- Successful commands atomically update provider state.
- Failed commands leave provider state unchanged and do not store a global UI error.
- `useVfs` outside `VfsProvider` throws a clear development error.
- Provider commands now include `moveNode`, `copyNode`, `moveNodeToTrash`, `restoreNodeFromTrash`, `deleteNodePermanently`, `emptyTrash`, `getTrashEntry`, and `listTrashEntries`.

Konqueror integration:

- `Konqueror` reads the shared VFS through `useVfs()`.
- VFS timestamps remain absolute ISO UTC instants for mutation, ordering, Shell output, and deterministic tests. Konqueror's modified/deleted-time presentation alone converts those instants through the browser/host local timezone using `Intl.DateTimeFormat`; no fixed offset or named production timezone is stored or applied.
- It does not create a private `createInitialVfsState()` store.
- Generic Konqueror launch carries the explicit `open-konqueror-start` Runtime intent and opens the virtual `about:konqueror` Start Page. Explicit Home, Documents, Trash, `open-directory`, and `open-sysinfo` intents override that default and enter their target directly without an intermediate Start Page visit.
- Existing Konqueror instances process only new launch request ids. Start Page, Home, Documents, Trash, `open-directory`, and `open-sysinfo` requests use the same history navigation, clear selection and operation errors, preserve clipboard, and do not mutate VFS.
- If text editing, an input dialog, destination-transfer dialog, or a confirmation dialog is open, external Home, Trash, and `open-directory` launch requests are marked handled but blocked. Konqueror remains focused, keeps drafts/input intact, and shows an internal message asking the user to finish the current operation.
- Navigation state is local to the Konqueror React component, not Window Manager, Application Runtime, Desktop state, VFS state, or browser storage.
- Konqueror resource presentation is application-local: `ResourceViewMode` is exactly `tree | icons`, with Tree View as the user-facing evolution of the former detailed list. Each new Konqueror seeds that local mode from the global `konquerorResourceViewMode` Desktop Preference, defaulting safely to Tree; an explicit Tree/Icon toolbar or View-menu change updates the future-instance default without live-syncing existing windows. Tree and Icon zoom are likewise independent per-window authorities, seeded respectively from `konquerorResourceTreeZoom` and `konquerorResourceIconZoom`; an actual active-mode Zoom In/Out change updates only that mode's future-instance default. Navigation, intents, minimize, virtual desktop switches, Show Desktop, and resize retain the instance values. Sort, selection, and all other content zoom systems remain non-persisted.
- Icon View consumes the immutable direct-child `sortedDirectoryChildren` projection. Tree View is a separate recursive VFS projection rooted at the current Resource location without rendering that root itself: `visibleTreeRows` traverses expanded directories depth-first in pre-order, applies the current sort independently to every sibling group, and carries stable node id, parent id, depth, expansion state, current child presence, last-sibling, and ancestor-continuation metadata. Every normal hierarchical VFS directory is expandable regardless of current child count; `expanded` and `hasChildren` remain separate facts. VFS `childIds` remain canonical/public order and are never sorted or mutated by Konqueror.
- Sorting supports Name, Size, Type, and Modified Time with ascending/descending direction. Directories are always grouped before text files. Name comparison is locale-independent case-folded string comparison with original-name and stable node-id tie breaks; Size uses VFS UTF-8 byte size; Modified sorting uses raw ISO instants and leaves invalid timestamps last, independent of local display formatting.
- Resource selection is an immutable, deterministic `selectedNodeIds` membership list of stable VFS node ids plus a runtime-only stable `rangeAnchorNodeId`, owned by each exact Konqueror instance and shared by Tree and Icon renderers. Ordinary primary item clicks replace membership and establish the anchor; Ctrl+primary item clicks toggle membership and establish the target as anchor even when it removes the last selected node. Shift+primary click replaces membership with the inclusive anchor-to-target range, while Ctrl+Shift+primary click adds that inclusive range without toggling its existing members; both preserve the anchor. A true blank-area click clears all membership and the anchor, while a primary blank-area drag past the four-pixel threshold starts the local marquee gesture. Selection and anchor never enter Desktop Preferences or history.
- `expandedTreeNodeIds` is immutable runtime-only membership owned by one exact Konqueror tab session. New tabs start collapsed; expansion neither navigates nor adds history, survives parent collapse/re-expand, navigation away/back, view switches, resize, and virtual-desktop changes, but never enters preferences or browser storage. An empty directory may therefore be expanded with no child rows; a later shared-VFS child insertion appears immediately beneath it, while a collapsed empty directory remains collapsed. Losing the final child never auto-collapses or prunes expansion membership. Only deleted, missing, or non-directory nodes are pruned; a moved valid directory may remain inactive until it is reachable from a later Tree root. The current formal `activeResourceVisibleNodeIds` is direct sorted child ids in Icon mode and the flattened `visibleTreeRows` ids in Tree mode.
- Tree hierarchy presentation consumes `VisibleTreeRow` metadata only. `depth` produces fixed-width gutter segments; `ancestorContinuation` controls per-row vertical continuation segments; and `isLastSibling` maps every current row, including direct children of the unrendered Tree root, to a T-junction or final elbow. The connector topology is CSS border/background geometry in each row, never Unicode glyph authority, DOM parent/child measurement, a fabricated root row, or a cross-row graph overlay. Adjacent vertical segments overlap by one pixel so list-row separators cannot break a continuation. Every row reserves a fixed expander slot and post-slot icon gap, so files and directories keep their icon/name alignment. The square CSS plus/minus control is presentation over the existing expansion authority and retains its established event isolation.
- The native `.konqueror-directory-viewport` is the sole scroll and clipping owner; Tree and Icon roots are its relative-positioned content surfaces. Marquee pointer capture, rectangle, and preview are owner-local to that surface. Client coordinates convert to viewport content coordinates using the viewport rect and scroll offsets, then use positive-area intersections. Icon View measures each item's full DOM hit rect; Tree measures the rendered `.konqueror-tree-label` border box only. Plain marquee preview/commit replaces membership and clears the range anchor; Ctrl marquee uses the pointer-down baseline plus current hits and preserves that valid baseline anchor. Each move recomputes current hits in `activeResourceVisibleNodeIds` order, so items left by the rectangle do not path-latch. Preview never enters the navigation reducer; pointerup commits once, and cancel/lost capture/unmount discard it. Drag points outside clamp to the viewport and may commit the clamped result; native scrollbar gutters do not initiate the surface gesture. Edge auto-scroll is deliberately absent.
- Range order is `activeResourceVisibleNodeIds`, supplied by the current Tree or Icon presentation rather than VFS insertion order, paths, filenames, DOM order, or a cached anchor index. Sorting recomputes the next range from the anchor's stable id and the new visible order. Collapsing a Tree branch or switching Tree to Icon immediately retains only visible membership and clears an anchor that became hidden, so commands cannot act on visually hidden descendants. Changing view, zoom, sort, and live re-sorting retains still-visible membership; navigation clears selection context, while Reload retains visible membership and preserves the anchor only while it remains visible. Selection membership and focus/current item remain separate. Tree keeps row-level selection semantics and full-row ordinary pointer/context ownership, while only its Name label renders selected paint and supplies its marquee geometry; the expander hit zone exclusively owns expansion. Konqueror's canonical keyboard target is the currently mounted Tree or Icon directory surface, which is programmatically focusable; existing ordinary Arrow navigation resolves a single next item from that same active sequence, collapses multi-selection, and establishes that target as the new anchor. Tree Left/Right reuses that exact-one current selection authority and the existing expansion authority: Right expands a collapsed directory, then selects its first visible direct child when already expanded; Left collapses an expanded directory, otherwise selects a visible parent. The unrendered projection root is never selectable, and hierarchy keys never navigate Location or history. Shift+Arrow, Ctrl+Shift+Arrow, and modified Left/Right range semantics are deliberately absent. Tree full rows and Icon cells retain item ownership, including their explicit-target double-click behavior; right-click behavior stays on its existing item/background paths.
- Konqueror item drag uses source-owned Pointer Events and the existing four-pixel gesture threshold, coordinated by one runtime-only desktop drag provider. A selected-member drag freezes the full `activeResourceVisibleNodeIds`-ordered group; an unselected item becomes the sole selection only when the gesture activates. Drag sessions retain raw visible-order ids separately from recursive Move/Copy roots, so selected ancestors cover descendants without changing selection. Pointer capture remains on the source while `elementFromPoint` resolves a stable destination: an eligible folder item wins first; a true blank area in a normal registered Resource surface resolves its stable `currentDirectoryNodeId`; a file item, header, scrollbar, special resource, or other desktop target is invalid. The candidate Konqueror surface must be visible, non-minimized, and on the current virtual desktop. VFS capability and execution remain authoritative. Desktop Trash is the only registered desktop special destination: it is not a fake writable folder, ignores modifiers, and sends the frozen raw drag ids to the source Konqueror's existing Move to Trash confirmation, which retains the formal normalized mutation roots and shared atomic mutation. A no-modifier normal-folder/background drop freezes source/target window ids, source-parent snapshots, and target NodeId into a measured desktop-transient action menu; Shift, Ctrl, and Ctrl+Shift at pointerup directly select the same atomic Move, Copy, and Link executor respectively, while Alt/Meta combinations retain the menu. DnD never reads or writes the shared clipboard. Folder, Resource-background, and Desktop-Trash highlights plus the compact pointer-events-none drag ghost are transient presentation state, not selection. Tree targets may expand after a 700ms drag hover through that exact window's existing expansion authority and stay expanded; a 24px top/bottom zone scrolls only the exact Resource viewport by 12px every 60ms and re-resolves the DOM target after each step. Timers, pointer capture, ghost, highlight, popup ownership, and the temporary Escape capture listener are cleared on every drop, cancellation, unmount, or target loss. Cross-Konqueror Tree/Icon drops work on the current virtual desktop only; hover does not activate or raise the target window.
- VFS Links are first-class leaf nodes with their own stable id, parent, name, and modified time plus a stable `targetNodeId`; they are virtual identity references, not host symlinks or path snapshots. The pure resolver follows Link chains with a visited-id guard. Target rename and move preserve a Link, target Trash makes it unavailable, Restore revives it, and permanent target deletion leaves a Broken Link. Open, Preview, and Open in New Window resolve the final target only after successful resolution; Rename, Copy, Move, Trash, Restore, and Permanent Delete operate on the Link node itself. Copying a directory shallow-copies contained Links with the same target ids and never copies or retargets target contents. Tree renders a Link as a leaf even when its target is a directory; a Link is draggable but cannot receive children or file drops. Link Here consumes raw ordered drag ids without ancestry pruning, creates per-source Link nodes atomically in the frozen destination, and leaves clipboard state untouched.
- Selection-scoped Copy, Cut, Move to Trash, Trash Restore, and Permanent Delete accept one or more selected ids. Their targets are projected from membership through `activeResourceVisibleNodeIds`, never membership insertion order or a first selected fallback. Open, Preview, Rename, and Properties still require exactly one selected id. The shared session clipboard snapshots ordered per-operation-root entries, each with a stable node id and its own source-parent snapshot; Copy and Cut may therefore include normal items from different Tree branches. Copy/Cut and recursive Trash moves prune descendants already covered by a selected ancestor, but Multi-Open deliberately keeps every explicit target. Paste validates every entry, then performs its ordered VFS copy/move batch atomically: stale sources, collisions, and cycles reject the whole batch. Copy Paste retains the clipboard, while a successful Cut Paste clears it. Trash Restore and Permanent Delete remain restricted to top-level Trash entries because only those nodes own Trash restore metadata. No clipboard or selection data is persisted.
- Edit-menu Copy Files and Move Files are separate direct operations, not Copy/Cut plus Paste automation. Clicking either command captures the exact owner WindowId, current directory identity, visible-order selected stable ids, normalized recursive operation roots, and each root's source-parent snapshot in a window-local destination-dialog request. Changing a later selection cannot retarget that request. Submit resolves the entered absolute path through `resolveKonquerorAbsoluteDirectoryLocation`, then requires a live, ordinary, writable VFS directory; the current resolver intentionally accepts neither relative input nor `file:` URL input. The request revalidates all live source ids/parents and delegates to the same DnD/VFS `copyNodes` or `moveNodes` batch authority, so recursive folders, Links, collisions, same-directory behavior, protected nodes, Trash exclusion, and self/descendant-cycle safety retain their existing atomic semantics. Success closes only the owner dialog, leaves navigation unchanged, preserves captured source selection for Copy, and clears the initiating selection for Move. It neither reads nor writes the shared Konqueror file clipboard, Klipper/DesktopSession text clipboard, or host filesystem.
- Konqueror file-operation Undo is a nonpersistent desktop-session `KonquerorFileUndoProvider` shared by all Konqueror windows. It stores strict-LIFO, operation-based VFS descriptors rather than whole-VFS snapshots: each descriptor carries stable node ids, original and post-operation parent/name expectations, and, for destructive create/copy/link inverses, a recursive semantic fingerprint that includes identity, topology, file content, and link target but deliberately excludes timestamps. Create Folder/Text File, Rename, Paste Copy/Move, DnD Copy/Move/Link, Copy Files/Move Files, and Move to Trash record exactly one successful user batch. Undo performs a single VFS candidate transition and only pops after success; conflicts, missing/replaced nodes, or safety-guard failures leave both VFS and history unchanged. Moved nodes may retain later content edits because their inverse is non-destructive; created/copied/linked roots are never removed after any semantic change. Restore from Trash, permanent deletion, Empty Trash, and editor writes do not create history entries. There is no Redo, Ctrl+Z binding, persistence, whole-state snapshot, path-only identity, or Undo-generated history entry.
- Multi-node VFS mutations are evaluated against an unpublished candidate state in deterministic target order and committed once only when every target passes the existing copy/move/collision/cycle/Trash validation. A failed or stale member leaves shared VFS and the clipboard unchanged. Destructive batch success clears the initiating selection context; live VFS selection retention removes deleted or moved ids from other exact Konqueror instances. A selected-member context click preserves the group; an unselected-member context click replaces it with that exact node.
- Window Manager emits a monotonic, nonpersistent focus-request id for an open, activate, restore, cross-desktop focus, desktop return, or explicit already-active activation. The id reaches Konqueror through `ApplicationHost`, so QuickLaunch can hand focus back from Kicker even when `isActive` did not change.
- Konqueror responds only to an activation request or explicit transient command/popup/modal completion. It schedules one local post-event focus attempt, never installs a document/window keydown listener, and never focuses again for passive VFS revisions, sort state, view state, or selection updates.
- An input, textarea, select, button, link, menu item, or contenteditable control inside Konqueror retains its own DOM focus. App-local dialogs and the context menu block directory handoff; closing them can return focus to the directory surface when Konqueror remains active.
- Tree and Icons are transient directory-view commands: after either command commits its view transition, Konqueror issues one local forced handoff so the newly mounted directory surface receives focus on the next animation frame. Location and Sort controls remain persistent interactive controls and never use that forced path.
- Konqueror owns one nonpersistent application-menu value: `location`, `edit`, `view`, `go`, `bookmarks`, `tools`, `settings`, `window`, `help`, or `null`. The dropdowns are command surfaces only. Location orders `New Window`, `New Tab`, `Print`, and `Quit`; New Window launches one independent instance from the active tab target, while New Tab calls the shared blank-tab command for this exact window. Tools is exactly `Open Terminal`, `Find File...`: terminal launch reuses the Context Menu's canonical directory planner against the current active-tab directory and is disabled for blank, file, Trash, and other virtual targets; it never falls back to another tab or a `file:` URL. Find File uses the existing explicit multiple-instance KFind launcher without touching Konqueror navigation, selection, or VFS. Window is exactly `New Tab`, `Duplicate Current Tab`, `Detach Current Tab`, and `Close Current Tab`: duplicate starts a fresh target-only history, detach carries the exact `TabSession` in a window-scoped Runtime launch intent before the source reducer removes it, and the latter two disable for a one-tab window. Print and every current-resource command route through the active tab. Edit reuses existing VFS clipboard, file-operation Undo, dialog, Trash, permanent-delete, and Properties controllers. Undo is enabled only when the shared history has a reversible top entry and no local blocking dialog is active; Copy Files and Move Files remain selection-aware direct operations. - `KonquerorBookmarksProvider` is the sole desktop-owned bookmark authority. It exposes an immutable ordered tree of generic string locations, persists only that tree in its own versioned localStorage record, and is shared by all Konqueror instances. Bookmark and Folder nodes retain stable ids. The Bookmarks menu recursively projects the tree's existing mixed sibling order: folders become icon-bearing submenus and bookmarks become icon-bearing `open-bookmark` actions carrying only a stable bookmark id. On execution, the exact invoking Konqueror instance performs its existing `navigateToLocation` path against the live Bookmark lookup; only a synchronously accepted target records one visit through the Provider. Rejected or deleted ids neither navigate nor update metadata. `bookmark-editor` is a normal singleton Application Runtime window under that same Provider: its selection, expansion, search, and field drafts are UI-local, while all rename, location/comment edit, creation, deletion, and reorder mutations use the Provider's stable-id APIs and write-through persistence. Search projects ancestors without persisting expansion, no-result state is presentation-only, and external Store revisions refresh untouched fields without overwriting a local field draft. It never records visits.
- Context Menu and Application Menu retain the shared Konqueror command availability and callbacks. Directory Open enters a folder or the default internal Preview Component by node kind; File -> Open keeps this default path. File delegates creation, Open, Edit, Properties, and the generic immediate-close request; Edit delegates Rename, clipboard, Trash, Restore, permanent-delete confirmation, and Empty Trash; View dispatches the existing view/sort reducer; Go uses stable-id navigation; Help launches the existing About application through Application Runtime.
- `toolbarProfile.ts` derives the Konqueror toolbar from the resolved `KonquerorView` plus its selected Previewer, never from scattered filename checks: directories, `trash:/`, and `sysinfo:/` use `resource-manager`; `about:konqueror`, local KHTML, and external HTTPS use `web`; Embedded Text and Markdown use `document`; Image and MIME-recognized Media use their dedicated profiles. The shared renderer owns the fixed-order icon inventory and classic separators, while navigation actions retain their current Konqueror callbacks and Resource/file-preview clipboard actions retain the existing VFS clipboard authority.
- The final content contract has six resolved modes: Resource (ordinary directories, Trash, and My Computer), Document (Embedded Text and Markdown), Local HTML (KHTML), External HTTPS, the Start Page, and MIME-recognized Media (audio/video). The four toolbar profiles define only their button inventory; the resolved mode remains the authority for availability, Home/Up resolution, printing, security, and the selected zoom state. Home resolves to the stable `/home/user` target from all six primary modes, becoming unavailable only when that exact Home target is already current or navigation is otherwise blocked.
- Each profile contains `Up, Back, Forward, Home, Reload, Stop | Cut, Copy, Paste | Print | Zoom In, Zoom Out`. Resource Manager appends `Icon View, Tree View`; Web appends `Security`; Document and Media have no trailing content-specific controls. The right-aligned KDE icon calls the existing explicit `open-konqueror-start` launcher path, which creates a fresh Start Page window rather than invoking ordinary reuse. Resource Manager's Icon/Tree controls and Zoom are active for directory and Trash resource renderers. Print and Zoom are also active for the application-owned Start Page, KHTML, Embedded Text, and Markdown roots; external HTTPS has its own parent-controlled iframe viewport Zoom while Security is active for the resolved `about:konqueror`, local KHTML, and owned external HTTPS views. Early KDE 3.0 intentionally omits Download; later KDE3.x KGet-oriented controls are outside this target. Media shows only the common navigation, clipboard, and visible-but-disabled Print action; playback controls live in one shared compact KDE3 control strip below the media stage rather than in the toolbar. Stop is enabled for the exact known pending external HTTPS or media load/playback state. The View menu and toolbar dispatch the same local directory reducer rather than maintaining parallel view state.
- In mobile layout the persistent Konqueror menubar is presentation-hidden, while its command model and callbacks remain mounted for desktop and shortcut paths. The shared toolbar renderer instead resolves one compact action group by stable IDs: `Up`, `Back`, `Forward`, `Home`, `Reload`, and `Stop`, followed by a flexible spacer and the existing New Konqueror Window launcher. Clipboard, Print, view, zoom, content, and toolbar separators are not rendered in that mobile group; the Location Bar remains a separate dock band.
- Resource zoom is discrete and local to one Konqueror instance. Each view remembers its own `small | normal | large | extra-large` level: Icon View uses `24/32/48/64px` icons with corresponding `88x66`, `104x76`, `132x98`, and `156x118px` minimum cells; Tree View uses `12/16/20/24px` node icons and `20/22/27/32px` minimum rows. `normal` is the existing default appearance. New instances seed those independent local levels from the persisted Tree and Icon defaults; an actual Zoom In/Out change writes only the active mode's default and never live-syncs existing windows. Zoom changes only resource-item geometry through CSS data attributes, never a transformed application viewport, and does not create a history entry. Tree headers and columns remain fixed; selection, sorting, VFS clipboard state, node actions, and stable node-id identity are unchanged.
- Embedded content capabilities are derived from the resolved view plus Previewer, not from a filename or toolbar profile alone: `about:konqueror` and local KHTML are `internal-web`; Embedded Text and Markdown are `document`; directories, sysinfo, unavailable views, and `external-web` have no embedded capability. Internal Web and Document each keep their own instance-local `75 | 90 | 100 | 110 | 125 | 150` percent zoom value, defaulting to `100`; they survive navigation but are not part of history or persistence. CSS `zoom` applies only to the exact owned content root, leaving Konqueror chrome and scrollbars at normal size; no `transform: scale()` is used for application-owned content. Resource Icon/Tree zoom remains independent.
- Presentation is owned by each Konqueror instance: Resource remembers separate Tree and Icon levels, Document remembers its content level, Internal Web shares a level between Start Page and local KHTML, and External HTTPS remembers a separate parent-side viewport level. Navigation, Back/Forward, Reload, Stop, and cross-mode transitions never copy these values into history or another Konqueror window.
- The Print action is available only for those application-owned embedded roots. `KonquerorPrintProvider` owns one screen-hidden, Desktop-sibling print surface, outside DesktopWindowLayer and every WindowFrame. A request carries its monotonic request id, exact WindowId, and an `about`, `{ file, previewerId }`, or pure `{ text, title, content }` safe document descriptor; it never reads bounds, WorkArea, ScreenArea, screen viewport, or live preview DOM. `flushSync` commits the matching surface before one browser-native `window.print()` call, and `afterprint`/failure clears it without an effect-driven second print. The print surface renders the same Start Page/KHTML/Markdown/Text React semantic components in normal document flow, resets screen zoom to `100%`, removes screen borders/outline/shadow, and keeps height unconstrained with visible overflow so the browser print engine, rather than a WindowFrame or scroll viewport, paginates it. WindowFrame, toolbar, Location bar, status bar, Kicker, Desktop, siblings, and other Konqueror instances are excluded. KHTML continues to print the inert sanitized React rendering, Markdown prints its rendered representation, and Text preserves line breaks while print-only `pre-wrap`/`overflow-wrap:anywhere` prevent long-line clipping. External HTTPS iframe content remains Print-disabled because the parent never accesses cross-origin frame DOM.
- Konqueror history is per tab and records only Konqueror-owned targets: Location submit, Back/Forward, Up, Home, Reload, launch intents, and internal Open. New Tab starts with `about:blank` alone; navigating away then Back restores its blank viewport and empty Location presentation. Duplicate Current Tab starts with only the active target and never clones Back/Forward stacks; Detach Current Tab moves the full history/session to the newly allocated window. Back/Forward never call iframe history APIs. A cross-origin iframe may follow links or redirects internally, but the Location bar, caption, and outer history remain the last canonical URL Konqueror owned; parent code does not inspect its URL, title, DOM, redirects, or history. External Up uses the URL pathname hierarchy, preserves scheme/authority/userinfo/port, clears query/hash, and never ascends a hostname. Home is derived from the resolved location rather than its shared toolbar profile: Resource, Document, local KHTML, external HTTPS, Start Page, and Blank locations target `/home/user`. Reload never appends history: external Reload creates a fresh iframe key from the canonical URL plus an instance-local monotonic generation, while internal and VFS reload retain their existing target/presentation state.
- External load state is local to the exact Konqueror component: `loading`, `loaded`, or `stopped`, tagged by canonical URL and generation. Only a matching iframe `onLoad` settles a pending request, and a newer navigation, Reload, Back/Forward, Stop, or unmount invalidates stale events. Browser iframe `error` events are not a reliable cross-origin load-failure signal and are deliberately not used for remote lifecycle state. `Page loaded.` means only that the frame load lifecycle was observed; it does not prove HTTP, TLS, XFO/CSP, rendered content, or final-URL facts. There is no timeout or cross-origin probing. Stop unmounts an exact pending iframe, preserves owned address/history/caption, and exposes `Loading stopped.` until Reload starts a fresh generation. It cannot control unknown iframe-internal navigation.
- External HTTPS keeps the fixed Web toolbar: Security and parent-side viewport Zoom are enabled while an iframe is mounted; Cut/Copy/Paste and Print are disabled; Download/KGet is absent. External Zoom is an instance-local `75 | 90 | 100 | 110 | 125 | 150` presentation value, defaulting to `100`, outside history and retained across Reload, Stop, and owned navigation. It scales the iframe itself from a clipped fixed parent viewport with inverse width/height, so a remote responsive page receives the corresponding viewport size. It is not browser-engine native page zoom and never reads or modifies remote DOM, CSS, or scroll state. The iframe remains `sandbox="allow-forms allow-scripts"` with no same-origin, popup, top-navigation, download, or device capability. There is no fetch-to-HTML path, proxy, backend, remote DOM access, frame-history access, remote print, or XFO/CSP bypass. Remote sites may refuse embedding through browser security policy, including X-Frame-Options or `frame-ancestors`, but this static build cannot reliably determine the exact reason.
- `getKonquerorSecurityInfo` is a pure resolver over the owned resolved view, selected previewer, and known external load state. The KDE SSL Information dialog is available for `about:konqueror`, local KHTML, and external HTTPS only. About/local views state that they are not secured with SSL and show their owned location/type. HTTPS shows only its owned canonical location, `HTTPS`, hostname, explicit-or-default port, and the known `Loading`/`Page loaded`/`Loading stopped` lifecycle. It does not claim certificate validation, encryption success, HTTP success, final redirect destination, TLS version, cipher, issuer, fingerprint, or certificate details; detailed certificate information is explicitly unavailable in this static web build. The dialog is state local to its exact Konqueror instance, closes on an owned location change, uses the existing modal layer, and does not alter the iframe sandbox or inspect iframe DOM/history.
- The Konqueror application-menu popup remains in its exact `WindowOwnedPopupLayer` portal. Each top-level opening, switch, and reopen receives a monotonically increasing local request id. The popup mounts hidden and non-interactive until the shared pre-paint measurement hook reads the current trigger rect and popup dimensions, then clamps screen-layer coordinates before revealing that exact request. Create New, View Mode, and Sort use the same transient owner-local submenu state, grace-close timer, ScreenArea clamp, and right-edge left flip; no default `(0,0)` or stale coordinates are visible after rapid switching.
- Back, Forward, Up, and Home toolbar buttons are transient navigation commands. After a command that is available completes, they reuse Konqueror's existing forced local directory-focus request; no Window Manager activation token is needed because the application is already active. Navigation still owns selection/history semantics, while Location and the View menu retain their persistent native focus behavior.
- Konqueror permits only one local popup menu at a time. Opening an application menu dismisses a context menu and right-clicking the directory dismisses an application menu. Modals take precedence and prevent application menus. `useApplicationMenuDismissal` provides the temporary capture-phase outside-pointer listener without consuming the click, while Escape and completed transient menu commands close the menu and request the existing directory-focus handoff when appropriate.
- Properties is a read-only, single-node Konqueror modal opened from the shared command surface. Its state stores only the selected stable node id; Name, type, parent location, full path, byte-size label, created time, and modified time are derived from the latest VFS state through public queries on every render.
- Properties reuses the existing browser-local timestamp formatter and Tree type/size semantics: text files use canonical UTF-8 byte size, directories show `-`, and invalid timestamps show `-` without changing the stored VFS instant.
- Rename, Move, Save, Trash, and Restore retain the node id, so an open Properties dialog follows current metadata and paths. Permanent deletion changes that dialog to a controlled unavailable state instead of rebinding it to selection or crashing.
- Properties is a modal interaction boundary: navigation, view/sort, file operations, clipboard commands, and external directory intents are blocked while it is open. Closing Properties leaves the existing selection and clipboard unchanged. The dialog is local component state, has no persistence, and performs no VFS mutation.
- Konqueror context menus are application-local popup state, not VFS or Window Manager state. An item menu stores a stable `clickedNodeId`, a synchronously captured visible-order `targetNodeIds` selection group, and client pointer coordinates; a background menu stores the current stable directory id plus coordinates. They never store a row index, path, node snapshot, or React event.
- Tree rows and Icon View items right-click an unselected target into a one-item selection before opening the shared context menu, while right-clicking an already selected member preserves its group. Right-clicking a directory background clears selection. The menu emits command ids only: Konqueror dispatches those ids to the same activation, clipboard, Trash, Restore, permanent-delete confirmation, Properties, and creation callbacks used by the toolbar.
- Resource item context menus lead with `Open`, `Open in New Window`, and `Open in New Tab`. Open and Open in New Tab use the physically clicked stable node id, never a mismatched current selection; the latter adds one active session with that folder or preview target and leaves its source tab unchanged. Open in New Window preserves the established explicit-instance plan, including selected-group planning for an already-selected item, and never changes the source tab array. New tabs never clone source history, selection, or Tree expansion. Neither tabs nor their active selection are persisted, and no browser-native tabs are created.
- Ordinary filesystem directory item and background menus additionally expose `Actions > Open Terminal Here`. The folder action resolves the physically clicked stable directory id at execution time; the background action resolves that owning Konqueror instance's current directory id. The pure planner rejects files and nodes in Trash, then derives the live canonical VFS path with `getVfsPathForNode` and calls `launchNewApplicationInstance("konsole", { intent })`. The request is stored by the Runtime against the specific allocated Konsole window before mount, so repeated commands cannot share a transient cwd. Links are intentionally not an Open Terminal Here surface in this phase. No VFS mutation, navigation, terminal transcript injection, URL conversion, or host shell API is involved.
- `Create Folder` is an explicit-target command: it freezes the menu request's `clickedNodeId` as the dialog parent, never reuses `targetNodeIds`, current selection, or a path. On submit it resolves that stable folder id against the current VFS, so a rename or move follows the same folder while a deletion, file replacement, Trash location, or duplicate name fails in the still-open dialog. The existing VFS filename validation, collision check, stable id allocation, timestamps, and one shared-state publication remain authoritative. Successful item-menu creation does not select the new folder, alter the range anchor, navigate, or auto-expand a collapsed Tree branch; normal shared-VFS projection and sorting expose it immediately beneath an expanded target.
- Context menu descriptors are pure `action`, `separator`, or one-level `submenu` entries. Text-file menus use `Preview in >` and `Open with > KWrite`; directory menus do not expose file preview/open-with menus. Preview content uses the same two submenus with a checkmark on the active renderer. Every row uses the same marker/label/arrow grid, including empty marker slots, so submenu parents and ordinary commands share a label origin. Normal item menus otherwise expose Rename, Cut, Copy, Move to Trash, and Properties; Trash menus otherwise expose Restore, Permanent Delete, and Properties. `Create Folder` is absent for files, Trash entries and descendants, sysinfo, and other special presentations. Normal backgrounds expose New Folder, New Text File, and Paste; the Trash background exposes Empty Trash only.
- Open submenu state is local to `KonquerorContextMenu`. A parent row and its nested panel form one hover family; leaving schedules a `140ms` close only, while entering either member cancels it. The timer is cleared on an action, dismissal, menu close, or unmount. The menu uses no permanent global pointer or keyboard listener, and its shared position helper flips and clamps both axes inside the Konqueror client surface.
- Konqueror content now separates a single `overflow:auto` directory viewport from a sibling non-scrolling popup layer. Tree and Icon directory surfaces fill the viewport, so a Tree list's unused area remains an intentional local context-menu surface while its sortable header stops propagation. The popup layer is measured and clamped in content-root coordinates and is never portaled above other Window Manager windows; its box cannot contribute to directory `scrollWidth` or `scrollHeight`.
- A temporary capture-phase pointerdown listener from the existing application menu dismissal hook closes the popup without consuming the target click. Escape closes only the popup, and viewport scrolling closes an open popup rather than attempting to track a scrolled row.
- Navigation, view/sort changes, modal commands, and VFS changes that remove a context target from the current directory close the menu. Rename keeps its stable target id valid; Move, Trash, Restore, and Permanent Delete require reopening the menu in the new command context. Konqueror only prevents the native `contextmenu` event on its directory rows/grid/background surface; address-bar and other browser text inputs retain their native menus.
- Rename, create, Paste/Move, Restore, KWrite save, and other VFS updates re-derive the visible sorted projection without a refresh. Sorting and view changes never add navigation history entries or clear the clipboard.
- History stores stable VFS directory/file node ids plus virtual `sysinfo`, `about-konqueror`, and external-web targets with a history index rather than copied nodes, content, filenames, or path strings. A file entry also carries its selected Previewer id as view state; file node id remains the location identity.
- The current path is derived from VFS parent links for VFS targets and from the canonical URL for an external-web target.
- Back and Forward move the history cursor only and do not add entries. They skip invalid directory/file history identities after leaving them.
- Successful directory or Preview navigation appends its stable target, truncates forward history when needed, clears selection and errors, and syncs the location draft to the normalized presentation path. Switching Previewer for the current file replaces that entry in place, so Back immediately returns to the preceding location and Forward restores the last chosen Previewer.
- Navigating to the current node clears errors without duplicating history.
- The Location field is an editable draft separate from canonical navigation identity. `about-konqueror` history entries carry `addressPresentation: blank | canonical`: generic Start Page launch records `blank`, while a typed `about:konqueror` records `canonical`. This state is replaced in the existing entry when the same Start Page target is revisited, never becoming a second history location. Back/Forward and Escape restore the entry's presentation, while all business logic continues to read the target type and canonical resolver.
- A failed Location submission restores the current committed presentation exactly once while leaving the actual focused input in its editing session. The reducer records the failure separately, and the next `set-location-draft` is owned by the user input and clears that stale error; it is never continuously overwritten by error or focus state. Escape uses the same one-shot restore boundary.
- A generic `open-konqueror-start` request also carries a transient Konqueror-local Location-input focus request. The shared latest-request/rAF handoff gives that explicit launcher request priority over content focus without selecting text or installing global listeners. Typed `about:konqueror`, Back/Forward, and Start Page link returns continue to request the Start Page scroll surface, while successful Location Enter navigation resumes the destination content surface.
- The Location bar has one form-submit authority for both Enter and the Go button. It synchronously captures the visible draft before navigation and resolves allow-listed `about:konqueror`, `sysinfo:/`, `trash:/`, absolute VFS directory/text-file paths through public VFS queries, and HTTPS external-web locations without consulting the current view/profile; it never changes the browser URL. The Go pointer path keeps focus within the form until that same submit runs, so a blur-driven canonical-draft refresh cannot replace the user's target. All other `about:` forms and `http:`/file/data/javascript protocols remain controlled invalid-location failures.
- Each Konqueror instance owns a two-slot DockArea between its Menu Bar and content: Toolbar/Location is the default order, and Location/Toolbar is the only alternate order. The existing KDE3 line grips use primary-pointer capture with a four-pixel threshold; drag preview reorders only those two owner-local bands, commits only when released inside the DockArea, and otherwise cancels. There is no floating surface, Desktop/body portal, global pointer listener, or cross-window live dock state. `konquerorDockOrder`, `konquerorResourceViewMode`, `konquerorResourceTreeZoom`, and `konquerorResourceIconZoom` are narrow fields in the existing versioned Desktop Preferences record: valid explicit changes silently seed future Konqueror instances, while already-open windows retain their own local presentation. Loading is lazy and safe; missing, invalid, unavailable, or unreadable storage falls back to Toolbar/Location, Tree View, and normal Tree/Icon zoom; a failed write never rolls back the current window. The preferences do not persist window ids, geometry, history, locations, dialogs, selection, external lifecycle, or Document/Internal Web/External Web zoom, and they have no cross-tab synchronization. Dock order and Resource presentation remain stable through content/profile navigation, minimize/maximize/resize, and virtual-desktop visibility without changing Location drafts, history, external iframe lifecycle, or printing.
- Navigation failure stores the `VfsError`, preserves the current directory and history, and retains the attempted location draft so it can be corrected.
- Up resolves the current target's VFS parent id rather than splitting a display path. The seeded hierarchy keeps real directory identities for `/ → /home → /home/user`, so Resource Up follows those parent ids until the actual VFS root, where it becomes unavailable; Home remains the separate `/home/user` navigation target. The `trash:/` protocol root remains an Up root, and a Preview's Up action enters its containing directory. Rename, Move, and Trash relocation preserve current/history identity and refresh displayed paths from VFS. Permanently deleted history ids are pruned; a current deleted Preview remains controlled/unavailable until navigation leaves it.
- Reload re-queries the current VFS node from the latest VFS state and does not increase VFS revision. This phase does not add an iframe reload/stop controller for external-web content.
- Directory view uses `listVfsDirectory` and keeps `childIds` order.
- File Preview derives the current text node through public VFS queries. `previewModel.ts` keeps the small renderer allow-list: every VFS text node supports `embedded-text` / Embedded Advanced Text Editor; `.html`/`.htm` additionally support and default to `khtml` / KHTML; `.md`/`.markdown` additionally support and default to `markdown` / Markdown Renderer. Filename extension only chooses a Preview Component; VFS text-node type remains the association boundary.
- `KonquerorPreviewHost` mounts exactly one focusable, read-only scroll surface for Embedded Text, KHTML, or Markdown. All renderers read latest VFS content, so KWrite save, Rename, Move, Trash, and Restore update the visible presentation without a copied content snapshot. A rename keeps a valid selected Previewer; only an invalid renderer falls back to the new default.
- KHTML is a KDE3-inspired component label, not the native KDE engine. Its local parser maps only a small safe structural allow-list to React nodes. It drops scripts, forms, style, media, SVG, frames, embeds, resource elements, and all untrusted attributes; it never uses raw HTML injection or inline document CSS. Markdown remains a small local React-free parser for headings, paragraphs, emphasis, lists, blockquotes, inline/fenced code, rules, links, and images; raw HTML in Markdown remains inert text.
- Local KHTML and Markdown share `documentResourceResolver.ts` for document-relative references. A relative VFS resource resolves against the current document's VFS parent directory, never the repository's physical path. Absolute VFS paths, dot segments, and root-clamped parent traversal use the existing VFS path authority. Existing VFS files, directories, and image files navigate through the same Konqueror location pipeline as the Location bar, in the invoking instance's active tab and normal history. Image references render only when the current VFS snapshot resolves to an allow-listed image asset URL; missing, non-image, unsupported, and remote image references remain controlled placeholders. There is no resource cache, Blob URL, browser path fetch, remote image fetch, CSS resource loading, metadata, or persistence change.
- Only canonical HTTPS links are passed to Konqueror's existing external-web navigation authority. `javascript:`, `data:`, `file:`, other schemes, empty references, and query-bearing VFS references are non-actionable. Fragment-only references are classified but remain non-navigating until document-anchor support exists; a VFS reference with a fragment currently navigates its document path and defers the fragment. This resource boundary is independent of the sanitizer: KHTML still has no script, event-handler, iframe, or raw DOM execution route.
- Command dialog state is local to Konqueror and uses a discriminated union for `closed`, `new-folder`, `new-text-file`, and `rename`.
- Dialog state stores stable node ids for parent or target nodes. On submit, Konqueror re-derives the latest VFS path through `getVfsPathForNode`.
- Background New Folder calls `createDirectory` through `VfsProvider`, stays in the current directory, and retains its established new-node selection behavior. Folder-item Create Folder uses the same VFS authority with its frozen clicked folder id but intentionally preserves the pre-existing selection and anchor.
- New Text File calls `createTextFile` through `VfsProvider` with empty UTF-8 content and `text/plain`, stays in the current directory, and selects the new file id.
- Rename calls `renameNode` through `VfsProvider`; node id, parent id, and history entries remain stable.
- Renaming the current file keeps the file view open and syncs the address bar to the newly derived path.
- Renaming to the same name is a successful no-op: the dialog can close, state reference and `revision` remain unchanged.
- Mutation errors such as `INVALID_NAME` and `ALREADY_EXISTS` are stored only in the command dialog and never enter `VfsState`.
- Command timestamps come from an injectable command environment. Production uses `new Date().toISOString()`; tests use a fixed ISO string.
- File-operation clipboard state is session-owned and shared by mounted Konqueror components. It stores `empty` or one ordered `{ mode, entries }` snapshot, where every operation-root entry captures its stable `nodeId` and its own `sourceParentId`. It never uses `navigator.clipboard`, browser storage, Window Manager state, Application Runtime state, or VFS state.
- Copy and Cut project selection through the active visible Resource order, normalize ancestor-covered descendants through the shared recursive-operation-target helper, validate every root, and atomically replace the shared clipboard only after the complete entry plan succeeds. The raw selected membership remains independent from operation roots; Cut retains it only for the existing pending presentation, never as Paste mutation authority.
- Copy Paste re-derives latest source and destination paths from every ordered entry, verifies each entry remains in its captured source parent, calls the atomic VFS batch copy authority, selects the copied roots, and keeps the clipboard. Cut Paste uses the same per-entry validation and atomic VFS batch move authority, selects moved roots, and clears the clipboard on success. Same-directory Cut Paste follows the VFS no-op move rule per entry and still clears the clipboard when the batch succeeds.
- Paste is only available in ordinary directory views. It is disabled in Trash, Preview, and while an internal command or confirmation dialog is open. Conflicts such as `ALREADY_EXISTS` are shown as local operation errors and do not modify history.
- Move to Trash is available for one or more selected, non-protected ordinary Resource items, including independently resolved cross-parent Tree rows. Hierarchical selection may legally contain both a directory and descendants; before this recursive mutation is submitted, the ordered selection is normalized to minimal selected ancestry roots through stable VFS `parentId` chains. Covered descendants are not duplicate mutation roots, while the raw selected snapshot and its count remain unchanged in the confirmation dialog. The frozen dialog stores both raw selected ids and normalized operation roots, so later selection changes cannot alter the pending mutation. Actual stale roots still fail atomically with Move-to-Trash-specific wording. Copy and Cut reuse the same normalization when building clipboard entries; Multi-Open deliberately does not prune explicitly selected ancestor/descendant targets.
- Move to Trash success clears selection, preserves navigation history, and clears the local clipboard if it referenced the moved node or any descendant of a moved directory.
- Konqueror presents the canonical Trash directory as the allow-listed `trash:/` protocol. It is a presentation alias, not a VFS node: history stores the same directory node id used by VFS, typed backend paths canonicalize to `trash:/`, and nested nodes display as `trash:/relative/path`.
- The toolbar, Desktop Trash icon, and typed `trash:/` all navigate to that same node. Back and Forward therefore retain their normal stable-id behavior alongside directory and `sysinfo:/` history. `trash:/` is a protocol root, so Up is disabled there and nested Up stops at `trash:/` instead of exposing backend ancestors.
- Trash browsing is read-only: directories can be entered and UTF-8 text files can be previewed, but New Folder, New Text File, Rename, Edit, Save, Discard, Cut, Copy, Paste, Move to Trash, F2, Delete, and file-operation Ctrl shortcuts are disabled.
- Trash root rows show metadata from `listTrashEntries`: current Trash display name, original location resolved from `originalParentId`, deterministic deleted timestamp, size, and type. If the original parent can no longer be resolved, Original Location displays `Unavailable`.
- The Trash root empty state says `The Trash is empty.`; ordinary empty Trash subdirectories still use the normal empty-folder wording.
- Restore is available for selected direct children of the Trash root with metadata. It calls the atomic `useVfs().restoreNodesFromTrash` authority, stays at `trash:/`, clears selection on success, and reports conflicts or unavailable original folders inline. Nested descendants of a trashed directory remain browseable but are not independent Trash entries and therefore do not expose Restore or Permanent Delete.
- Delete Permanently is available only for a selected direct Trash root entry. It opens a Konqueror-internal irreversible confirmation dialog, calls `useVfs().deleteNodePermanently`, clears selection, defensively clears clipboard references to the deleted subtree, and removes deleted node ids from navigation history.
- Empty Trash is available only at the Trash root when it has children. It opens an irreversible confirmation dialog, calls `useVfs().emptyTrash`, preserves the Trash root, clears selection and affected clipboard state, and prunes deleted ids from Back/Forward history.
- Trash subdirectories remain browseable and read-only, but Restore, Delete Permanently, and Empty Trash are disabled there; users must return to the Trash root and select a top-level entry.
- Ctrl+C, Ctrl+X, Ctrl+V, and Delete are handled only inside Konqueror's client/list area when no text input, command dialog, or confirmation dialog owns the interaction. Address-bar and Preview text copy remain browser-native.
- VFS `revision` changes naturally re-render Konqueror because view data is re-derived from provider state.
- Minimize, virtual desktop switching, Show Desktop, maximize, restore, and To Desktop keep the mounted Konqueror component, so navigation, Preview, and dialog state are retained.
- Minimize, virtual desktop switching, Show Desktop, maximize, restore, and To Desktop also keep the local clipboard and confirmation/input dialog drafts because the component remains mounted.
- Start Page Home Folder and Toolbar/Go Home retain the real `/home/user` target in their current Konqueror. Kicker/K Menu Home starts new `/home/user` windows; Kicker/K Menu generic Konqueror starts a new `about:konqueror` window. My Computer and Desktop Trash start new `sysinfo:/` and `trash:/` windows.
- `about:konqueror` and `about:blank` are React virtual targets, not VFS nodes or stored HTML files. The former is the Start Page; generic launch intentionally presents an empty Location field while retaining that exact target, while typed navigation visibly presents `about:konqueror`. `about:blank` is a real empty history target with an always-empty Location presentation, no resource capabilities, and caption/tab label `about:blank`. Its Starting Points route Home Folder to `/home/user`, Storage Media to `sysinfo:/`, Trash to `trash:/`, and Settings through the existing KControl Runtime action. Network Folders and Applications are visibly unavailable; no `network:/`, `applications:/`, device, or host-filesystem virtual location is introduced.
- `getKonquerorCaption` remains a pure location-to-base-caption resolver. It derives Start Page, My Computer, Trash-root, Root Folder, current directory basename, and file/unavailable captions from the current location and latest public VFS node. Previewer changes never affect its base caption; Rename/Move update it through stable ids. Generic Window Manager display-caption derivation is the sole suffix owner, and WindowFrame, Taskbar, grouped representative buttons, popup rows, and Window Menu all consume the same final `window.title`.
- Konqueror also has a typed `{ type: "external-web", canonicalUrl }` history target for user-entered HTTPS locations. The location bar resolves internal `about:konqueror`, `sysinfo:/`, `trash:/`, and absolute VFS locations before considering external URLs; supported `https:` URLs and bare dotted hostnames canonicalize through the platform `URL` API, while `http:`, script/data/blob schemes, and plain text remain controlled invalid locations. The canonical URL is the address display and history identity; captions use its hostname because cross-origin document titles cannot be read.
- `KonquerorExternalWebView` is the only remote content host. It uses a native iframe with `sandbox="allow-forms allow-scripts"` and `referrerPolicy="strict-origin-when-cross-origin"`; it deliberately grants no same-origin, popup, download, device, or top-level-navigation capability. Local VFS HTML and Markdown remain the separate inert KHTML/Markdown preview pipeline and never use an iframe or network request. There is no fetch-to-HTML path, backend/proxy, CSP/X-Frame-Options bypass, or remote-content reinjection. Cross-origin iframe URL changes and document titles are not observable by the parent, and a remote site's `X-Frame-Options` or `frame-ancestors` policy may prevent embedding.
- Closing one Konqueror removes only that window and unmounts its local navigation/dialog state; remaining instances and the shared file-operation clipboard remain. A new generic launch starts a fresh `about:konqueror` history. Saved in-memory VFS changes remain until page refresh. Navigation history has no browser History API or storage persistence.
- There is no close confirmation or autosave in this phase.
- Multi-select, Restore To, drag-and-drop, right-click menus, Undo, Save As, upload/download, binary editing, and persistence are not implemented.

## Shell Core

Phase 5.32 makes Konsole a KDE 3 style multiple-instance application while retaining the Phase 4.1-4.10 browser-safe Shell core. Konsole remains a UI and adapter layer only; the tokenizer, parser, command registry, execution, cwd fallback, transcript creation, command history, command semantics, and completion algorithms remain owned by `src/shell`.

Layering:

- `src/shell` owns tokenization, parsing, command registry, command execution, session state, transcript state, and shell-specific errors.
- The tokenizer and parser do not import VFS or React.
- The completion partial lexer is separate from the formal tokenizer. It accepts edit-time states such as unclosed single or double quotes and returns token replacement ranges for the current caret, but it never executes commands and does not replace the parser.
- Read command execution uses only VFS public query APIs such as `getVfsNodeById`, `getVfsPathForNode`, `resolveVfsPath`, `listVfsDirectory`, and `readVfsTextFile`.
- Path completion also uses only VFS public query APIs and reads the caller's current `VfsState` for each Tab press. It does not cache a VFS snapshot and does not change VFS revision.
- Write command execution uses a React-free `ShellMutationPort` interface. The Shell core never imports `VfsProvider`, React Context, Window Manager, Application Runtime, `child_process`, `node:fs`, or host shell APIs.
- Shell output is plain text data, not JSX, HTML, ANSI, or executable content.

Mutation port:

- `ShellExecutionEnvironment` can provide `mutations` and `now`.
- Read-only commands still work with the historical three-argument `executeShellInput(session, vfsState, input)` call.
- `mkdir`, `touch`, `append`, `cp`, `mv`, `trash`, `restore`, confirmed `permanent-delete`, and confirmed `empty-trash` require a mutation port; if it is absent they return `MUTATION_UNAVAILABLE` and do not call the clock.
- The mutation port exposes only Provider-shaped commands: `createDirectory`, `createTextFile`, `appendTextFile`, `copyNode`, `moveNode`, `moveNodeToTrash`, `restoreNodeFromTrash`, `deleteNodePermanently`, and `emptyTrash`.
- The port accepts paths and options only. It never exposes `nodesById`, `childIds`, `trashEntriesByNodeId`, or a direct state setter.
- Mutation commands use an injected `now()` timestamp. Production Konsole supplies `new Date().toISOString()` through the environment; tests inject fixed ISO strings.

Konsole UI:

- `src/apps/konsole` owns the React window content, menu bar, terminal viewport, prompt line, command input, and UI-only history navigation cursor.
- The application registry defines `konsole` with unsuffixed base title `Konsole`, multiple-instance behavior, preferred bounds `700 x 460`, and minimum size `420 x 260`. The generic caption resolver derives `Konsole`, `Konsole<2>`, and later collision ranks; Konsole never generates suffixes.
- QuickLaunch Konsole and K Menu System -> Konsole are explicit launchers and call `launchNewApplicationInstance("konsole")` without an intent. Konqueror's `Actions > Open Terminal Here` supplies its directory intent. Ordinary Runtime `launchApplication("konsole")` preserves its generic focus/reuse behavior for multiple applications.
- Each mounted Konsole owns a component-local `KonsoleShellWindowState`: stable `ShellSessionId` records, `activeSessionId`, a monotonic session-id allocator, and the original launch working directory. Each record owns a `ShellSessionState`, draft, history-navigation cursor, completion state, selection request, paste queue, and selection state. There is no WindowManager terminal-state map or module-level current terminal.
- The first record is slot 1, named `Shell`; later records receive the lowest unoccupied positive slot and use `Shell No. N`. Rename changes only the label, never the stable id or slot. Closing the active record chooses the nearest previous remaining tab and releases its slot; the final record cannot close, so window Quit remains the explicit way to close a one-shell Konsole.
- A new Shell is created inside the current window, starts empty, and uses that window's original initial working directory. With no launch intent this is Home; a valid window-scoped working-directory intent initializes the first shell before the first prompt renders and is retained only as the new-shell cwd seed. No post-mount `cd`, global next-cwd variable, transcript clone, or prompt-only override is used.
- VFS revision changes do not recreate the Shell session. Each submitted command passes the current `vfs.state`, the Konsole mutation port, and the production clock to `executeShellInput`.
- `src/apps/konsole/createKonsoleMutationPort.ts` adapts `useVfs()` Provider commands to `ShellMutationPort`. It does not create a private VFS store and does not call pure VFS mutation functions directly.
- Command dispatch resolves the active stable session id against the current window-local session collection before invoking the shared Shell core. Quick submissions therefore update the correct transcript/history without stale render closure or cross-tab mutation.
- A physical blank or whitespace-only Enter is a Konsole submission concern, not a fake Shell command. Konsole appends a prompt-only transcript entry with an empty command text and the current prompt-path snapshot; it does not call a VFS mutation, append `commandHistory`, or create output chunks.
- The input draft and Up/Down history navigation cursor are UI state only; they are not stored in `ShellSessionState`, `VfsState`, Window Manager, or Application Runtime.
- Each `ShellSessionState.commandHistory` is that Shell's single command-history store. `history [count]` receives an immutable pre-invocation snapshot from the executor, so it never displays itself but is appended normally after execution. Closing a Shell destroys only its history; minimizing, Show Desktop, virtual-desktop changes, and tab switches do not.
- Completion candidate state is per-Shell UI state. It stores the current completion context key and candidates only; it is not written to transcript, command history, VFS, Window Manager, or Application Runtime.
- Konsole's terminal body is a flex column: a natural-height, shrinkable `min-height: 0` transcript scroll viewport, then a bounded completion region, then a non-shrinking active input row. With short content, the input follows transcript naturally and unused space remains below it; when content overflows, completion consumes transcript space above the input rather than moving the active prompt outside the terminal.
- The completion region wraps candidates and has its own bounded vertical overflow for large sets. Before Tab changes this layout, Konsole records whether the transcript was at bottom and synchronously restores only that bottom position after the layout commit; manually scrolled transcript positions are not forcibly changed.
- Multi-line paste is Konsole input-stream behavior, not Shell syntax. A React-free planner merges clipboard text at the current input selection, recognizes LF, CRLF, and lone CR physical terminators, and preserves all non-terminator text verbatim.
- Each terminated physical line is queued as one raw Shell input. A blank physical line is consumed once as a prompt-only transcript entry, while the final unterminated segment remains in the single-line input draft and never enters transcript/history until the user submits it. A single trailing terminator ends only its preceding command; a second terminator represents one blank physical submission.
- The Konsole-local FIFO queue assigns deterministic numeric ids. Its processor consumes one queue head per committed React cycle, marks that id before dispatch, and therefore cannot replay a command because of StrictMode or unrelated rerenders.
- Each queue head calls the same `executeShellInput` dispatch path as Enter after resolving its owning stable Shell session, with the latest `vfs.state` and Provider mutation port. The subsequent command therefore sees its own previous cwd and VFS mutation results; failures do not stop later queue items.
- Multi-line paste clears completion candidates and resets local history navigation, then applies the final draft caret through the existing one-shot selection request. Single-line paste stays browser-native.
- Konsole's six-menu application surface is Session, Edit, View, Bookmarks, Settings, and Help. Session lists New Shell, New Window, then a separator and Quit. Bottom New Shell and Session -> New Shell share the same window-local command callback and allocator; Session -> New Window alone uses the explicit `launchNewApplicationInstance("konsole")` path through the mounted prototype. View lists only Rename Session, which targets the current `activeSessionId`; tab double-click instead supplies its clicked stable id. Both paths reuse the same app-owned dialog, validation, and rename authority. Quit uses the Application Host's exact-window close callback; there is no app-global terminal shutdown or current-instance lookup by caption.
- `KonsoleBookmarksProvider` is a desktop-level authority independent from `KonquerorBookmarksProvider`, using the same immutable bookmark-tree domain and safe versioned persistence adapter under `kde3-web-desktop.konsole.bookmarks.v1`. It projects mixed ordered children recursively into the Konsole Bookmarks menu and supplies a separate singleton `konsole-bookmark-editor` runtime window whose root is `Konsole Bookmarks`. A saved leaf carries only a stable bookmark id; execution live-resolves it in the Konsole Store, builds a safely quoted `cd` command, and passes it to the exact invoking window's active Shell through the normal `submitKonsoleShellInput` dispatch path. This preserves transcript/history/prompt behavior and records a visit only when the Shell accepts the `cd` command with exit code zero. Manual `cd`, invalid paths, a missing live id, and opening the menu do not record visits.
- Edit -> Copy and Paste use the shared `DesktopSession` text clipboard. Copy is available only for a nonempty terminal/input selection and writes through the existing clipboard history and best-effort browser bridge. Paste reads the in-session clipboard authority and inserts at the controlled command input selection/caret without submitting a shell command. The single-line menu paste normalizes physical line breaks into spaces; it deliberately does not enter the existing native multi-line paste queue. Konsole adds no Ctrl+C/Ctrl+V shortcut routing in this menu phase.
- `konsoleSchemas.ts` owns a small readonly catalog: KDE3 light `Konsole Default` (black foreground, white background) plus Linux Colors, Green on Black, White on Black, and XTerm Colors. Schema state is per mounted Konsole window, shared by all of its Shell sessions, defaults for every new instance, and is not persisted or synchronized. It applies only terminal palette tokens for the current viewport/input/output stream classes; WindowFrame, menu chrome, geometry, terminal font metrics, and the shell parser are unchanged. The simulated terminal has stream color classes, not ANSI escape-sequence parsing.
- Konsole renders a compact bottom Shell tab bar in normal client layout. Its square New Shell control creates a session in the existing window; tabs select stable session ids; a compact close control closes only the active session when more than one exists. Double-clicking a tab opens an app-owned Rename Shell dialog with trimmed, nonempty, max-64-character labels; no browser prompt or host terminal exists.
- `formatKonsolePromptPrefix` is the shared prompt identity/path authority. Prompts append `$`; the active window reports `${prefix} - ${shellName} - Konsole` through Application Runtime `setWindowTitle`, allowing the generic caption collision resolver to manage duplicate titles without a Konsole-specific suffix.
- Minimize, virtual desktop switching, Show Desktop, maximize/restore, To Desktop, and overlapping windows keep Konsole mounted and preserve cwd, transcript, history, and draft.
- Closing one Konsole unmounts and destroys only that instance's Shell records, cwd values, transcripts, command histories, drafts, queues, and refs. Other Konsole instances remain mounted and unchanged. End Session resets all volatile runtime windows; the next Konsole is a fresh Home session with an unsuffixed caption.

Session state:

- Each Shell session owns an independent `ShellSessionState`.
- `cwdNodeId` stores a stable VFS node id rather than a cached path string.
- `transcript` stores immutable entries with deterministic numeric ids, raw input, prompt cwd path, output chunks, and exit code. Prompt-only entries use empty input and output while preserving the submitted cwd-path snapshot.
- `commandHistory` stores each non-empty submitted raw input, including repeated commands and `clear`.
- Shell-core whitespace-only input remains a no-op and returns the original session reference. Konsole's physical Enter submission layer separately turns it into a prompt-only transcript line without history or VFS side effects.
- `clear` clears visible transcript entries but does not reset `nextTranscriptEntryId`, avoiding id reuse after clearing.

Parser and commands:

- `tokenizeShellInput` supports whitespace splitting, single quotes, double quotes, empty quoted strings, and backslash escaping outside quotes and inside double quotes.
- `lexShellCompletionInput` supports partial command lines, cursor-in-the-middle replacement ranges, unclosed quotes, and backslash decoding for completion only.
- Unquoted shell operators and command substitution markers such as `|`, `&&`, `>`, `<`, `;`, `&`, backticks, and `$(` return `UNSUPPORTED_SYNTAX`.
- `parseShellInput` returns a `ShellCommandInvocation` with `commandName`, ordered args, and raw input. Command names are case-sensitive.
- The command registry is readonly and exposes `pwd`, `cd`, `ls`, `cat`, `echo`, `append`, `head`, `tail`, `wc`, `grep`, `find`, `stat`, `basename`, `dirname`, `tree`, `mkdir`, `touch`, `cp`, `mv`, `trash`, `restore`, `permanent-delete`, `empty-trash`, `history`, `clear`, and `help` in fixed help order.
- Unknown commands return exit code `2` and do not launch applications or inspect the host `PATH`.

Shell mutation target resolution:

- Creation targets normalize absolute or cwd-relative VFS paths, split parent/name, validate names through VFS rules, require an existing directory parent, and reject Trash parents.
- `cp` and `mv` treat an existing directory destination as a destination directory and retain the source name.
- If the destination does not exist, `cp` and `mv` treat it as a new path, split dirname/basename, and pass `newName` to the VFS Provider command.
- Existing file destinations are rejected; no overwrite, merge, force, or interactive replacement exists.
- Destinations ending with `/` must already be directories.
- Regular `cp` and `mv` reject sources inside Trash and destinations at or inside Trash. The `trash` command is the only Shell write command that places nodes in Trash.
- `mv source source` is a successful no-op and keeps VFS revision unchanged. `cp source source` is a conflict.
- Trash management targets resolve a user path to a top-level Trash entry by normal cwd-relative or absolute VFS path resolution, then require the node to be a direct child of the Trash root with `VfsTrashEntry` metadata.
- Trash management target resolution never uses `originalName` as the current path and never treats Trash descendants as independent entries.
- `permanent-delete` and `empty-trash` use explicit `--confirm` syntax instead of pending confirmation session state. The destructive command is fully represented in command history, there is no stale pending target, and unconfirmed commands never call the mutation port or clock.

CWD behavior:

- `createInitialShellSession(vfsState)` starts at `specialLocations.home`. Its optional initial canonical VFS path resolves once during session construction and becomes the stable `cwdNodeId` only when it names a directory; invalid inputs retain the normal Home/root fallback.
- If Home is unavailable, initialization falls back to root.
- Before every non-empty command, the executor validates that `cwdNodeId` still exists, is a directory, and is reachable from root.
- If cwd was deleted or invalidated by another VFS consumer, the executor falls back to Home, then root, emits a system warning, and resolves relative paths from that fallback directory.
- Valid Trash directories are still valid cwd values; the Shell does not auto-exit Trash.

Supported commands:

- `pwd` prints the current canonical VFS path.
- `cd [path]` changes cwd to a directory, using normal VFS absolute and relative path resolution.
- `ls [path]` lists a directory in `childIds` order, appending `/` to directories, or prints a file basename.
- `cat <path>` reads a UTF-8 text file exactly as stored.
- `echo [text...]` prints parsed arguments joined by one space plus a trailing LF. It does not perform variable, escape, or redirection behavior.
- `append <path> <text...>` calls Provider `appendTextFile`, which atomically appends UTF-8 text to the latest VFS file content, recalculates byte size, updates `modifiedAt`, and leaves id, parent id, created time, MIME, encoding, and directory order unchanged.
- `head [-n <count>] <path>` and `tail [-n <count>] <path>` use a pure line-preserving text segmentation helper. The helper preserves LF, CRLF, lone CR, empty lines, Unicode, and missing trailing newlines without trimming or adding output.
- The shared head/tail argument parser accepts default `10`, `-n 0`, and decimal non-negative safe integers; invalid counts return `INVALID_ARGUMENT`, while usage and unsupported options keep exit code `2`.
- `wc` counts preserved logical lines, whitespace-delimited words, and UTF-8 bytes. Its logical-line model intentionally differs from POSIX newline-character counting.
- `grep` performs literal substring matching. `-i` uses deterministic lowercase comparison, `-n` adds 1-based logical line numbers, and output preserves each source line terminator. No match exits `1` without stderr; usage errors exit `2`.
- `find` walks one VFS start node preorder depth-first through public node, path, and directory-listing queries. It emits canonical paths in `childIds` order and uses a local visited-id guard.
- `find -name` compares exact, case-sensitive current basenames; wildcard and regular-expression syntax remain literal.
- `stat <path>` resolves one current VFS node and prints only its real model metadata: canonical path, name, type, timestamps, direct directory item count, or text-file size, MIME type, and encoding. It does not fabricate POSIX permissions, owners, inode numbers, blocks, or access times.
- `basename <path>` and `dirname <path>` are pure lexical POSIX-slash operations. They do not resolve a VFS node and accept nonexistent paths.
- `tree [path]` reuses the same public-query preorder walker as `find`, then renders a deterministic ASCII-only hierarchy in current `childIds` order. The shared walker has a local visited-id guard for invalid repeated nodes.
- `history [count]` renders the current Konsole session's pre-invocation command history in oldest-to-newest order with stable 1-based numbering. It has no VFS dependency and does not persist after Konsole closes.
- `wc`, `grep`, `find`, `stat`, and `tree` receive the current `VfsState` for every execution, keep no search index or snapshot, and never change revision.
- `mkdir <path>` creates one directory. It does not support `-p`.
- `touch <path>` creates an empty UTF-8 `text/plain` file if missing. Existing files are a successful no-op and do not update `modifiedAt`.
- `cp <source> <destination>` copies files or directory trees recursively through VFS Provider `copyNode`; `-r` is not supported or required.
- `mv <source> <destination>` moves or renames through VFS Provider `moveNode` and preserves node ids.
- `trash <path>` moves a file or directory to VFS Trash through `moveNodeToTrash`, preserving Trash metadata.
- `restore <trash-entry>` restores a top-level Trash entry through `restoreNodeFromTrash`. Restore conflicts and unavailable original folders remain VFS-managed errors.
- `permanent-delete [--confirm] <trash-entry>` warns without mutation unless `--confirm` is the first argument. Confirmed deletion removes the complete Trash entry subtree through `deleteNodePermanently`.
- `empty-trash [--confirm]` warns without mutation unless `--confirm` is present. Confirmed emptying calls `emptyTrash`; an already empty Trash is a successful VFS no-op.
- `clear` clears the visible transcript and keeps history.
- `help [command]` prints a deterministic command list or per-command usage.

Shell and VFS sharing:

- The Shell receives the caller's current `VfsState` for each execution and does not copy or own a VFS store.
- Konqueror-created, renamed, moved, trashed, restored, deleted, or saved text files can be read by later Shell commands when Konsole passes the updated state.
- Konsole-created, copied, moved, touched, or trashed nodes are committed through the shared VFS Provider, so Konqueror and the desktop Trash icon update from the same state.
- Konsole append commands are committed through the same Provider; Konqueror can immediately open the appended file, and a later Shell `cat`, `head`, or `tail` reads the appended content.
- Konsole restore, permanent delete, and empty Trash commands use the same Provider state, so Konqueror Trash UI and the desktop Trash icon update from the same mutations.
- Read-only commands do not mutate VFS and do not change `revision`.
- Successful write commands follow the underlying VFS Provider revision rules. Failed and no-op commands do not consume ids or increment revision.
- Because cwd is a stable node id, moving or trashing the current cwd keeps the Shell session valid and the next prompt derives the cwd's new path from VFS.
- Restoring the top-level Trash entry containing the current cwd keeps the same `cwdNodeId`; the next prompt derives the restored path. Permanently deleting or emptying the subtree that contains cwd leaves the node unavailable until the next command triggers the existing cwd fallback.

Completion:

- The first token completes command names in the same fixed order as `help`: `pwd`, `cd`, `ls`, `cat`, `echo`, `append`, `head`, `tail`, `wc`, `grep`, `find`, `stat`, `basename`, `dirname`, `tree`, `mkdir`, `touch`, `cp`, `mv`, `trash`, `restore`, `permanent-delete`, `empty-trash`, `history`, `clear`, `help`.
- `help` completes its first argument from command names and does not provide completion after extra arguments.
- Path completion context is derived from command and argument index: `wc` and the final `grep` operand offer files, while `find`, `stat`, `basename`, `dirname`, and `tree` offer files and directories only for their one path operand. Patterns, counts, options, and `find -name` values are not completed. Existing command completion rules remain unchanged.
- Trash-entry completion is a separate context for `restore` and `permanent-delete` operands. It lists only canonical Trash-root children, preserves `childIds` order, supports relative names when cwd is `/home/user/.local/share/Trash/files`, supports that absolute backend prefix elsewhere, and never lists nested descendants as manageable entries.

Shell never accepts `trash:/`: it is a Konqueror-only presentation protocol. A shared Shell operand helper expands only `~` and `~/...` to the current Web Desktop home before existing VFS normalization, across all VFS path-taking commands. It does not support `~user`, environment variables, globbing, or host paths; `pwd` always reports the canonical VFS path. This is in-memory virtual storage only: there is no host `~/.local` access, `.trashinfo` implementation, or Trash persistence.
- Directory candidates append `/`; unique command candidates append a space; unique unquoted file candidates append a space.
- Multiple candidates use a pure longest-common-prefix helper. If the prefix extends the active token, Konsole updates only that token and preserves text after the caret; otherwise it displays candidates without changing the draft.
- Unquoted path insertions use backslash escaping for whitespace, quotes, backslashes, and shell-significant characters. Double quotes keep spaces literal and escape `"` and `\`. Single-quote completion skips candidates containing `'` because the current tokenizer does not support representing that inside single quotes.
- Candidate display is plain text inside the terminal viewport. It is not a dropdown, popup, button list, transcript entry, or history entry.

Terminal keyboard behavior:

- Tab runs completion only while the Konsole command input owns focus and IME composition is not active.
- Ctrl+L clears visible transcript through `clearShellTranscript` while preserving cwd, command history, `nextTranscriptEntryId`, current draft, and caret. It does not submit the string `clear` and does not add a history entry.
- Ctrl+A and Ctrl+E move the command input caret to the beginning or end of the current draft.
- Plain Home and End likewise collapse the input caret to the beginning or end. Modified Home/End, Delete, Backspace, Shift selection, Ctrl+C, Ctrl+X, and Ctrl+V retain browser-native input behavior.
- Transcript text remains selectable plain text and uses browser-native copy. Konsole does not emulate SIGINT, add a global Ctrl+C listener, or use the Clipboard API.
- Escape clears visible completion candidates without changing the draft or closing Konsole.
- ArrowUp and ArrowDown keep the existing history navigation behavior and clear stale completion candidates before moving through history.

## KCalc

KCalc is a multiple-instance Application Runtime application. Each explicit K Menu launch creates a fresh `0` calculator session; minimizing, desktop switching, Show Desktop, and restoring preserve each mounted reducer state, while closing one KCalc unmounts only that session.

- The application registry defines `kcalc` with unsuffixed base title `KCalc`, multiple-instance behavior, deterministic Hide All preferred and minimum bounds `273 x 282`, a fixed-size WindowFrame (`isResizable: false`), and generic `isMaximizable: false`. These capabilities are independent from `isDraggable`, so KCalc remains titlebar-movable. Generic caption resolution derives `KCalc`, `KCalc<2>`, and later collision ranks; KCalc never generates suffixes.
- K Menu Utilities -> KCalc is the only current explicit KCalc launcher and calls `launchNewApplicationInstance("kcalc")`. There is no KCalc QuickLaunch item, Desktop launcher, application-specific launch intent, or internal New Window command. Ordinary Runtime `launchApplication("kcalc")` retains its generic focus/reuse behavior.
- `src/apps/kcalc/calculatorCore.ts` is a React-free, per-instance state reducer. It stores display text, a nullable exact `radixEntry`, accumulator, pending binary operator, waiting-for-operand state, a separate current-pending-operand validity flag, an explicit error flag, an empty-or-finite memory register, an immutable `statisticsValues` numeric dataset, and a display-only result-history cursor. The explicit operand flag lets Dat commit the following numeric input as fresh while leaving its displayed count usable by a pending equals transition. `kcalcRadix.ts` is the separate pure integer boundary: it validates radix digits, preserves exact `BigInt` entry values, formats uppercase unprefixed signed-magnitude output, and permits an explicit guarded conversion back to `number` only inside the existing number-based calculator authority. Every mounted KCalc owns its own reducer and local menu refs; there is no WindowManager calculator map, module-level mutable calculator state, or memory/statistics persistence. `kcalcModeState.ts` remains a separate React-free per-instance presentation model for inverse, persistent hyperbolic mode, angle unit, and number base.
- Arithmetic remains an immediate pocket-calculator model, not an expression parser. A command dispatcher maps descriptor command ids to narrow unary, binary, percent, memory, Statistics, or scientific reducer transitions; physical slots and labels are never execution authority. Confirmed binary commands are Mod, IntDiv, xʸ, and x¹⁄ʸ; confirmed unary commands are 1/x, x!, x²/x³, √x/∛x, circular trigonometry, hyperbolic trigonometry, logarithms, and exponentials. `kcalcScientificMath.ts` is a React-free evaluator: it accepts only a scientific command id, finite entry value, and command-time angle unit. `kcalcStatisticsMath.ts` is a separate React-free read-only evaluator over `readonly number[]`; it receives no UI or mode state. Neither `eval`, `Function`, a host shell, nor a real process is used.
- Number formatting normalizes finite JavaScript results to deterministic, locale-independent display text and converts invalid or non-finite results to the contained `Error` state. Repeated equals is intentionally a no-op. The active keypad includes digits, decimal, four arithmetic operators, equals, C, AC, sign, Inv, confirmed Base Scientific commands, `%`, memory commands, and Statistics data commands. `%` keeps KCalc's documented contextual final-operation semantics: `+`/`-` treat the right operand as a percentage of the left, `*` divides the product by 100, `/` produces the left operand as a percentage of the right, and other pending commands follow equals. C, Error, digit-after-Error recovery, panel visibility, and mode toggles do not reset memory, statistics, or mode state; AC preserves memory, statistics, angle, and base while explicitly restoring NORM. The reducer remains the sole memory lifecycle authority: MS, M+/M- create or update a register, MC restores `null`, and MR only reads an existing register; the status row owns no duplicate memory flag.
- The KCalc menubar presents File, Edit, Constants, Settings, and Help in that order. File owns Close and Help owns `About KCalc` followed by historical `About KDE`; those launch independent Runtime `about-kcalc` and historical singleton `about-kde` windows rather than an inline calculator panel. Edit owns dynamic Undo/Redo plus Cut, Copy, and Paste, with stable `edit-*` command identities rather than label dispatch. A primary click on the recessed display invokes the same `edit-copy` command, preserving its state-derived Error no-op and shared DesktopSession clipboard path. `kcalcResultHistory.ts` owns only completed nonzero result values (`number | bigint`) and its KDE3 cursor: successful complete `=` actions prepend their canonical value, while zero, unary commands, queries, recalls, constants, clipboard commands, and mode changes do not append. KDE3 stores newest-first and displays the current cursor before advancing, so the first Undo repeats the latest result; Redo moves the same cursor in reverse. Later results prepend without truncating older entries. History navigation only replaces the displayed current amount through the active Base formatter and establishes a fresh-entry boundary; it never restores or clears pending arithmetic/Logic, memory, Statistics, constants, clipboard, Hyp/INV/Angle/Base, or any mode. The source-era MS and M+/M- paths invoke `EnterEqual()`, so their successful nonzero committed value also follows this history boundary. History belongs to an exact mounted KCalc, survives minimize/restore, is destroyed on close, and has no browser persistence or status UI. It exposes checkable panel toggles plus Show All, Hide All, disabled Configure Shortcuts, and Configure KCalc. Those visibility flags never reset KCalc mode state.

The standard-deviation evaluator uses squared deviations from the mean with denominators N-1 or N, not a cancellation-prone difference-of-squares formula. Six Store surfaces retain six separate slot and command identities. Toggling either mode changes neither calculator state nor required KCalc window width.

Generic task grouping, virtual desktop placement, minimize/restore, Show Desktop, Lock/Unlock, and End Session reuse the existing Shell infrastructure without KCalc-specific branches.

- KCalc Logic execution uses `kcalcLogicMath.ts`, a React-free evaluator whose operands and results are `bigint`; the reducer adds a tagged exact-or-fractional Logic pending operand rather than converting the complete calculator to BigInt. AND, OR, XOR, Lsh, Rsh, and Cmp are stable command ids and descriptors, not button-label dispatch. BigInt operators are used only on proven BigInt operands; Number bitwise coercions and fixed-width masks are prohibited. `Cmp(x)` is `-x - 1`; shifts are binary, negative counts reverse direction, and positive right shifts truncate toward zero. AND/OR/XOR return `0` if either ordinary-number operand is fractional, while complement and shifts reject fractions. The deterministic shift limit is `100000` bits, producing contained `Error` on larger counts rather than uncontrolled resource allocation. This Logic contract supersedes the earlier deferred-Logic notes in this section; Base entry/representation, Science, Statistics, Memory, layout, and four-slot status semantics remain unchanged.

- KCalc command availability has a separate pure current-operand domain classification: normal finite numbers and exact radix integers within the inclusive safe Number range are number-compatible; exact integers outside that range are exact-only; `Error` is unavailable. The UI uses this classification to disable only commands that must consume the current operand as `number`: ordinary binary arithmetic, implemented Base Scientific operations and percent, Memory writes, Dat, and decimal Science commands. Logic, Base conversion, sign, C/AC, Memory read/clear, and Statistics queries retain their independent availability rules. Core reducers continue their guarded conversion and produce `Error` if a programmatic action bypasses the disabled UI. Availability is derived per reducer instance and becomes available again immediately after a safe fresh entry; it creates no warning state, digit-length rule, status slot, or geometry change.
- `KCalcConstantsProvider` is application-level state beside, not inside, `DesktopPreferencesProvider`. It owns six always-present C1-C6 registers shared live by all KCalc windows in one mounted Desktop; calculator display, pending operations, modes, memory, and Statistics remain exact-window state. The same version-1 browser-storage document persists every `{ name, value }` record with no H2 migration: values are tagged finite `number` or exact `integer`, finite numbers serialize as round-trip decimal strings, and BigInts as canonical base-10 strings. No KCalc component or reducer reads/writes browser storage directly. Store captures the calculator's canonical number or radix-entry BigInt, never display text, writes through immediately, and establishes a fresh-entry boundary without finalizing arithmetic or Logic. Recall restores that typed value through the existing Base formatter, including exact oversized integers, and is a valid Error recovery path. C/AC/Error do not clear constants. Normal constant buttons show the persisted name and a `name=value` tooltip; their inverse surface remains Store. A right-click always targets the physical C1-C6 identity, including while INV makes it display Store. Set Name is bounded to six visible characters and changes presentation only. Choose From List atomically writes both historical built-in label and value without changing the current calculator display. Configure KCalc stages all six name/value rows and commits only on Apply or OK; names must be non-empty and no longer than six characters, values are explicit finite decimal literals (safe integers as numbers, oversized decimal integers as exact BigInts), and Cancel leaves provider state and persistence unchanged. The static built-in catalog itself is never persisted or editable. Keyboard constant shortcuts remain deferred.

## KWrite

Phase 5.31 makes KWrite a multiple-instance, single-document Application Runtime application. Every explicit K Menu KWrite launch creates a fresh Untitled window, while Konqueror `Open with > KWrite` creates a fresh exact-file window using its stable VFS node id. Ordinary Runtime `launchApplication("kwrite")` keeps its generic focus/reuse behavior; only explicit launcher and Open with paths request a new instance. Each mounted WindowId owns its independent document, dirty state, Find/cursor DOM state, dialogs, overwrite/close flow, and local baseline.

- The registry defines `kwrite` with initial base title `Untitled - KWrite`, preferred bounds `720 x 560`, minimum bounds `420 x 300`, and a resizable WindowFrame. K Menu Utilities provides KWrite without adding a desktop icon or QuickLaunch button. Generic caption resolution derives `Untitled - KWrite`, `Untitled - KWrite<2>`, and later ranks; KWrite itself reports only unsuffixed base captions such as `Notes.txt - KWrite`.
- Application Runtime remains generic. Konqueror sends `{ type: "open-text-file", nodeId }` through the existing request-id launch channel on a new KWrite instance. KWrite validates and consumes each request once; Runtime neither imports VFS nor interprets the intent.
- Konqueror's unified node activation path navigates directories and opens typed VFS file values using the default read-only Preview Component. The location union stores `{ type: "file", nodeId, previewerId }` in the same history as directory, `sysinfo:/`, and `trash:/` targets; paths and names are always re-derived from that stable id. `Preview in` selects an available renderer and replaces only the current file entry. `Open with > KWrite` accepts text-backed files only, so KWrite remains the only editor and cannot turn an asset into text. Supported `audio/mpeg`, `audio/ogg`, `audio/wav`, `video/mp4`, `video/webm`, and `video/ogg` asset URLs resolve to the MIME-specific Media previewer, which renders a native paused media element inside a black responsive stage plus one shared custom KDE3 transport strip. The strip owns Play/Pause, Stop, finite-duration Seek, Volume, Mute, and deterministic elapsed/duration labels; the native `controls` attribute is absent. Media uses the same current-tab navigation, per-tab node-id history, reload/stop, clipboard, and unmount cleanup paths; reload/stop reset playback without reloading the global window, tab switching or leaving the file pauses and cleans up the native element, and new mounts never autoplay. Waiting, ended, rejected-play, invalid, and unsupported states remain controlled per-tab state. There is no media application, Web Audio/DSP, visualizer, playlist, publication surface, or new Videos mount.

Image preview accepts supported-image asset URLs, with a matching legacy data URL accepted for the existing seed. No preview fetches a VFS path, reads URL bytes as text, or creates a Blob URL. Each reads the latest public VFS node each render, so KWrite saves and Rename/Move/Trash/Restore update content, path, and file caption without a new navigation. A permanently deleted current preview remains a controlled `File unavailable` page until Back leaves it; it never rebinds a same-name replacement node.

It prints through the existing typed Konqueror file-preview request, has no separate runtime or persistence, reports natural dimensions in its owning caption after load, and uses no object URLs, remote fetch, external application, pathname parser, or Window Manager sizing path. Its scroll surface centers each axis only while the rendered image fits that axis; an oversized axis starts at zero so the true image top and left remain reachable.

The mounted preview scroll surface, directory list, `sysinfo:/`, and `about:konqueror` pages are alternative local targets; interactive Location/menu/toolbar controls retain user focus. No document/window keyboard handler or custom scroll algorithm is installed.
- KFind default result activation does not use KWrite. It delegates both directory and text-file results to a new Konqueror instance; Konqueror remains authoritative for selecting its file Preview renderer. Konqueror's explicit `Open with > KWrite` creates a new KWrite instance instead.
- KWrite stores a stable VFS `nodeId` as the backing-document identity. Current canonical path, canonical name, optional presentation name, file content, Trash status, and availability are re-derived from public VFS queries. Its window/editor/print presentation may use `displayName ?? name`, while Save, Save As, overwrite checks, status path, and Runtime intent identity remain canonical. Rename, Move, Trash, and Restore therefore continue to track the same document without path identity or a private VFS copy.
- `documentModel.ts` is React-free and keeps the editor draft, normalized baseline content, baseline `modifiedAt`, current line-ending policy, mode, and status notice. Dirty is derived from draft versus baseline, not from whether a key was pressed.

It never writes `nodesById`, invokes a pure mutation directly, or keeps a Provider snapshot. A successful save refreshes the baseline and follows normal Provider timestamp, size, and revision rules.

Dirty documents retain their draft and enter conflict only when the backing text content or its uniform line-ending convention changes relative to the baseline. Rename, Move, Trash, Restore, and their `modifiedAt` lifecycle updates refresh location metadata without creating a conflict. Save is disabled in a true conflict until Revert explicitly reloads the latest file. Unrelated VFS revisions do not create conflicts.

Empty/no-terminator files use LF only for new user-created line separators. Mixed-ending files are deliberately read-only rather than silently normalizing the full file.
- Phase 5.3.1 adds a React-free replacement state model. Pending actions are plain data (`new`, `open-dialog`, or `open-node`), never callbacks, and receive local increasing ids so a Save or Discard continuation is consumed exactly once. Dirty New, Open, and a different Konqueror open-file request first show one KWrite-local Save / Discard / Cancel dialog.

Dirty Untitled, conflict, Trash, and unavailable drafts can use Save As to rescue editable local content. Cancel keeps the current draft and clears the pending action.

They use stable directory node ids for navigation, re-read the latest Provider state, list only VFS directories and text files, and use Home / Up navigation. Dialog state distinguishes the displayed `currentDirectoryNodeId` from an optional single-clicked `selectedDirectoryNodeId`: double-click or Enter on a directory changes current and clears selection; Save As resolves selected-or-current plus the unchanged filename field. Open accepts current Trash files for read-only viewing; Save As rejects Trash destinations.

Existing text files require an explicit Replace confirmation and retain their stable target node id; folders cannot be overwritten. The document binds to the resulting stable file id after either path.
- Direct K Menu launch creates a fresh editable, nonpersistent Untitled scratch buffer with no backing node and disabled ordinary Save. Save As is available for Untitled, including an empty buffer. A clean document can switch to a requested file, while a dirty request enters the replacement flow. File -> New and Ctrl+Alt+N continue to replace only the current document through that guard; they do not create a window. Tabs, multi-document windows, and native dialogs remain deferred.
- Phase 5.3.2 adds a generic Application Runtime close-request protocol. Definitions default to immediate close; only KWrite opts into `application-guarded`. Titlebar X, the window-menu Close command, and File -> Quit request closure through Runtime. File -> Close instead closes only KWrite's current document and resets that same editor to Untitled. Immediate applications commit with the established Window Manager close primitive; guarded requests carry a monotonic plain-data request id until the application commits or cancels that exact request. Reducer state stores request data only, never callbacks or promise resolvers.
- KWrite consumes each window-close request once. Clean documents commit immediately. Dirty documents show one app-local Save / Discard / Cancel confirmation: Discard commits without a VFS write, Cancel clears the request and preserves the draft, and ordinary Save commits only after Provider success. File -> Close reuses that same guard but has a document continuation: Save or Discard resets only the invoking editor to Untitled, while Cancel preserves it. Untitled, conflict, Trash, and unavailable dirty drafts use the existing Save As rescue flow; successful creation or explicit Replace then completes the same document or window continuation. Canceling Save As cancels only a window-close request. A new close request after Cancel receives a new id, so stale work cannot close a later request.
- Same-file KWrite windows share the normalized VFS node but never an editor buffer or loaded-content baseline. A save cleans only its own instance; a dirty sibling compares the live text against its own baseline and follows the existing content-based conflict protection. Metadata-only Rename, Move, Trash, and Restore updates do not create false text conflicts. Save As rebinds only the saving instance to its new stable node. End Session remains the existing explicit session-wide confirmation followed by a volatile runtime reset, rather than a per-document save manager.

Minimize, desktop switching, Show Desktop, resize, VFS updates, and launch requests do not replay a consumed close request. Browser/tab close remains outside this protocol: there is no `beforeunload`, browser confirmation, persistence, or recovery.

Ctrl+O, Ctrl+S, and Ctrl+Shift+S remain best-effort browser shortcuts; Ctrl+Shift+S has priority over Ctrl+S. Delivered KWrite shortcuts are matched on the app-root capture boundary and prevent browser defaults before acting, while an open KWrite dialog absorbs them rather than allowing a background action. The textarea retains native caret, selection, Home/End, and ordinary typing, while KWrite owns its bounded undo/redo history and project-clipboard Cut/Copy/Paste menu commands; there is no Keyboard Lock API, document/window keyboard listener, Clipboard API, storage, real filesystem, process, `eval`, or `Function` use.

Only while a dropdown is open, the hook observes capture-phase `document` `pointerdown` events and clears menus whose menubar does not contain the target. It never consumes the event, so the same click still activates another window or operates the desktop, Kicker, taskbar, or pager. The listener is removed on close and unmount; this is menu dismissal, not a permanent global keyboard or pointer policy.

A successful backing-file adoption from KWrite Open, Save As, or an external typed `open-text-file` launch intent records the resolved live snapshot only after KWrite establishes that backing node; failed, missing, unsupported, directory, and Untitled targets are not recorded. ## Desktop Preferences and KDE Control Center

Phase 5.4 introduces `DesktopPreferencesProvider`, mounted outside the Window Manager, Application Runtime, Kicker, and application host. It owns only the applied desktop preference value and a controlled `applyPreferences` API. It has no VFS, Shell, or runtime dependency. The Desktop bridges the applied `desktopCount` preference into WindowManager so changing the count is a single reducer reconciliation: current desktop is clamped, ordinary windows on removed desktops migrate to the last remaining desktop, and removed per-desktop focus/Show Desktop records are discarded.

- `DesktopPreferences` is a React-free value model with immutable defaults: `kde-classic` background, visible desktop icons, visible clock date, LCD clock look enabled, seconds and weekday hidden, blinking dots and the time-only frame enabled, and `desktopCount: 4`. A persisted v1 record without `desktopCount`, `lcdClockLook`, or the Phase 5.103 clock fields receives their formal legacy defaults, and other invalid count values are rejected. Existing taskbar filtering and per-desktop application cascade state remain keyed by the resolved numeric desktop id, so new desktops begin with fresh placement state.

The direct K Menu Control Center row launches it without adding a desktop icon or QuickLaunch entry.
- KControl starts on an unselected Home page. Its local tree is `Appearance & Themes -> Background` and `Desktop -> Behavior`; the tree is presentation-only and does not create a second preference authority. The existing desktop-icon preference remains keyed by `showDesktopIcons`.
- Panel settings are extracted into the singleton `configure-panel` application titled `Configure the Panel`, with its own taskbar entry and registry bounds. It now owns only `Show tasks from all desktops`; clock settings are presented by the separate `configure-clock` singleton titled `Configure - Clock`. Owner and group remain disabled because the VFS has no ownership or permissions model.

Time and size are evaluated before file content, while First Matching Line keeps its existing text-result snapshot behavior. Stable result `nodeId` ownership, live rename/move presentation, and new-Konqueror activation remain unchanged.

Missing paths and file nodes are rejected without a fallback search. The Result `In Subfolder` value is derived relative to the committed search root, with direct children left blank.

Rendering re-derives each result's current name, canonical path, parent path, type, and existing UTF-8 byte size from the latest VFS state. Rename and Move therefore update rendered metadata; permanently deleted ids disappear. Newly created matching nodes do not appear until the user runs Find again.

## Responsive Layout Foundation

`ResponsiveLayoutProvider` is the Desktop-level responsive authority. It derives `DesktopLayoutMode` (`mobile` or `desktop`) from logical viewport width and `DesktopOrientation` (`portrait` or `landscape`) from the current logical width/height, without user-agent or device-pixel-ratio detection. The initial mobile boundary is inclusive at `480` logical pixels; browser CSS viewport dimensions are divided only by the existing `--kde-ui-scale`. Browser/page zoom therefore changes the effective CSS viewport naturally and is never applied a second time by this model.

The provider exposes logical viewport width/height, the logical work area above the existing Kicker height, titlebar height, UI scale, and logical safe-area insets through `useResponsiveLayout`. Safe-area values originate at the unzoomed root `env(safe-area-inset-*)` bridge and are converted once into shell coordinates. They are foundation data only in this phase: no Kicker, window, or application padding is changed. The same responsive snapshot supplies `WindowManagerProvider` with its existing work-area and screen-area values, while direct standalone WindowManager tests retain the legacy resize fallback.

`#root` is the shared CSS/JS viewport bridge: its actual unzoomed border-box geometry is backed by `100vw`/`100dvh`, and `getCssViewportSize()` measures that element before falling back to `window.innerWidth`/`innerHeight` when bootstrap or tests have no usable root. `ResponsiveLayoutProvider` observes root size changes with `ResizeObserver` when available and also treats `window.resize` and `visualViewport.resize` as coalesced invalidation sources; all triggers feed one refresh pipeline and one root measurement authority. The stable `.desktop-shell` publishes `data-layout-mode` and `data-orientation`, so later mobile phases can add narrowly scoped CSS/consumer behavior without remounting Desktop, windows, VFS, locale, theme, or application state. `viewport-fit=cover` remains deferred until a later phase actually consumes edge-to-edge safe-area spacing.

Responsive changes are state-preserving geometry updates, not application remounts. A portrait-to-landscape-to-portrait transition such as `390x844 -> 844x390 -> 390x844` refreshes the logical viewport and Work Area, while WindowManager preserves window IDs, current virtual desktop, active identity, z-order, launcher metadata, application state, and the mode-specific normal/restore profiles. Desktop pointer sessions use the same logical coordinate path; titlebar drag and resize sessions cancel without committing their pending frame on `pointercancel` or lost pointer capture, just as marquee and touch sessions already do.

Phase 5.127 consumes that same `data-layout-mode` for the first mobile shell presentation. The Kicker remains one mounted panel and keeps the real K Menu, virtual-desktop pager, and locale-aware DigitalClock visible in a left Start-plus-Pager flow with a flexible gap before the right-aligned Clock; Quick Launch, Taskbar, and Clipboard are presentation-hidden with `display: none`, while Taskbar/Clipboard transient surfaces close when the mode changes to mobile. Pager buttons continue to come from the configured WindowManager desktop count and IDs. The K Menu keeps its desktop width and gold KDE3 surface on desktop, but mobile CSS clamps the panel and measured cascades to the logical viewport; its existing work-area scroll, right-first/left-fallback positioning, and keyboard/action state remain authoritative. No safe-area padding, touch gesture policy, WindowManager geometry, or application remount is introduced.

WindowManager now consumes the same `layoutMode` and logical Work Area without creating a second viewport authority. It keeps runtime-only `normalBoundsByMode` and `restoreBoundsByMode` profiles on each window, so desktop geometry is not overwritten by a mobile transition and maximized restore remains mode-specific. In mobile mode, managed windows default to an enforced maximized presentation with bounds exactly equal to the current Work Area; the stable `calendar` application ID is the sole normal-window exception. A Clock launch passes its logical anchor through the existing `initialBounds` path, and Calendar preserves that compact position above the Kicker while fitting its complete bounds to the usable Work Area; launches without an anchor retain the registry preferred size. Calendar remains fully contained when the Work Area is reconciled on desktop or mobile resize, and a shrink never causes a later viewport expansion to enlarge the compact profile automatically. For ordinary applications, their user `state` remains normal when they were normal on desktop, so the desktop normal profile remains restorable. Minimized windows remain minimized, close remains available, and mobile maximize/restore, drag, and resize requests cannot defeat the presentation; Calendar keeps the same disabled Minimize/Maximize policy while its Close action remains available. A mode transition preserves window state, active identity, z-order, virtual desktop, and application identity, while a Work Area change reapplies the policy-specific mobile presentation bounds. New mobile-first application windows retain their registry preferred bounds for a later desktop profile. The titlebar's existing `min-width: 0` text track and fixed control track remain the only shell overflow boundary; application-internal mobile layout and safe-area edge-to-edge consumption remain separate work.

The K Menu applies one centralized mobile availability policy to stable application, submenu, and command identities. Configure Panel, KCalc, Find Files, Bookmarks, Quick Browser, and Run Command remain visible but disabled in mobile mode, including their Most Used application projections; disabled submenu branches cannot open. Desktop availability and Most Used ordering remain unchanged.

Persistent first-party application menubars use the shared `application-menubar` semantic class. Mobile CSS hides only that horizontal application chrome and therefore reclaims its flex height; Kicker, titlebar system menus, popup menus, context menus, and dialog-owned menus are outside the selector. Konqueror, KWrite, Konsole, KCalc, and Control Center close their owner-local menubar request when `layoutMode` enters mobile, so a portal popup cannot outlive its hidden trigger. Returning to desktop reveals the same mounted application and preserves its non-menu state. Apps without a persistent menubar do not receive a placeholder.

Other managed applications consume the same `data-layout-mode="mobile"` presentation boundary without creating a second responsive authority. KWrite keeps native textarea editing and retains only Open, Save, Undo, and Redo in its compact toolbar; the omitted toolbar actions remain available through existing menus, shortcuts, or native editing paths. Konsole keeps its terminal as the text-selection surface and bounds the prompt while its transcript owns vertical scrollback. Control Center stacks its existing navigation tree above the selected module, KFind stacks criteria/actions while preserving all result columns in the result-table scroller, and Blog Tags stacks its existing tag/detail panes. KCalc uses smaller mobile-only layout tokens and an internal button-bank scroller only when optional columns exceed the client width. About, Calendar, Bookmark Editor, Blog, Article Reader, Configure Panel, and Configure Clock reuse their existing content surfaces and receive only containment/wrapping rules; no app state, command model, registry availability, or WindowManager policy is duplicated or changed.

## Desktop Internationalization Foundation

- `DesktopPreferences.locale` is the single persisted language preference. It uses the existing `kde3-web-desktop.preferences.desktop.v1` record; missing or invalid values normalize to English (`en`) without creating a second storage key or changing the preference schema version.
- The supported locale set is `en`, `zh-CN`, and `de`. `I18nProvider` derives the active locale from applied `DesktopPreferences`, exposes the typed `t(key, params)` translator, and synchronizes `document.documentElement.lang` without remounting the Desktop or its application windows.
- English is the canonical message schema. Chinese and German dictionaries are typed against the same key set, and lookup retains an English fallback boundary for incomplete future dictionaries. Interpolation is explicit and named, such as `Move to Desktop {number}`.
- Control Center owns the draft language selection and applies it through the existing Defaults / Reset / Apply lifecycle. Core shell localization extends the same typed dictionary to Desktop context/session surfaces, the K Menu and launcher descriptions, Kicker/taskbar/clock/clipboard labels, shared window-system menus and controls, Run Command, Calendar/Clock date presentation, About/system dialogs, and core Control Center chrome. Command IDs, tree identities, window routing, menu behavior, and application-specific body content remain unchanged.
- Konqueror's main UI, built-in `sysinfo:/` and `about:konqueror` surfaces, and its menu, toolbar, Location Bar, view, context-menu, Properties, Bookmark Editor, media, and security chrome resolve visible labels through the same typed translator at render time. Blog, KFind, KWrite, Konsole, and KCalc application chrome now uses the same `en`/`zh-CN`/`de` dictionaries, including generated dates, dialogs, status text, schema/category labels, and accessibility text. Locale changes rerender these consumers without recreating their content, query, terminal, editor, or calculator state. Canonical menu-model labels may remain English internally; command IDs, VFS names, paths, URLs, document content, terminal input/output, calculator expressions, search queries/results, and bookmark or Blog user data remain unchanged.
- Product and application names such as KDE, Konqueror, Konsole, KCalc, and KWrite remain brand-stable. Repository paths, VFS names, metadata, document contents, blog article text, terminal text, calculator values, search queries/results, and user-authored content are never translated by this UI layer.
- The UI font token keeps the existing KDE3 stack and adds ordered system CJK fallbacks (`Noto Sans CJK SC`, `Microsoft YaHei`, and `WenQuanYi Zen Hei`) without bundling font files or changing content typography.

## Touch Interaction Foundation

Shell touch input uses native Pointer Events through the small shared boundary in `src/input/pointerInteraction.ts`. Pointer type and layout mode remain separate: responsive presentation still comes only from the shared `layoutMode`, while touch and pen semantics are derived from the actual pointer event. Drag and resize surfaces use pointer capture and clean up on `pointerup`, `pointercancel`, lost capture, and unmount; marquee selection keeps the existing logical-coordinate conversion.

The shared long-press contract is one `500ms` delay with an `8px` browser client-coordinate movement tolerance. A second touch pointer, movement, cancellation, early release, or unmount cancels the gesture. A fired long press consumes the following synthetic click and native context-menu event so a context action cannot also activate the underlying icon or surface. Desktop icons use first-touch select and second-touch open; shell desktop/background long press reuses the existing context-menu boundaries. Application-specific long press remains deferred.

Touch target support is scoped to shell controls. Kicker Start, Pager, and Clock retain their existing click actions; K Menu rows use native tap activation, preserve vertical scrolling, and add a localized Back row only to nested mobile submenus. Mobile keeps the accepted disabled K Menu identities and enforces Close enabled with Minimize and Maximize/Restore disabled for visible windows; reducer and window-menu boundaries enforce the same policy. Desktop-layout titlebar drag and resize accept touch and pen through the existing geometry path, while mobile enforced-maximized windows remain non-draggable and non-resizable. `touch-action: none` is limited to titlebars and resize handles; the document, root, desktop surface, and menus do not globally disable browser pinch zoom.

Phase 5.130 consumes the same `layoutMode` inside Konqueror without remounting its window or application state. The persistent menubar is hidden in mobile presentation, while the compact toolbar keeps its stable navigation actions and New Konqueror Window control; the Location Bar and tab strip remain separate shrink-safe tracks. Details keeps its Name/Size/Type/Modified columns in an internal horizontal scroller, while Icon View derives a width-fitting grid. Tree hierarchy, navigation, context menus, dialogs, Properties, Bookmark Editor, sysinfo/about, image/text preview, and media playback semantics remain the existing boundaries with only mobile overflow, stacking, or wrapping presentation rules.

Konqueror resource touch handling uses the existing stable-node navigation and context-menu callbacks. A first item tap selects, a second tap on the selected item opens, and a held item or background invokes the existing long-press context boundary. Movement cancels activation and consumes the follow-up click; touch/pen input does not enter the desktop mouse marquee or drag state machines. The K Menu mobile Bookmarks policy, locale behavior, theme behavior, VFS/content state, and Window Manager semantics are unchanged.
## Markdown Publication Metadata

Markdown publication metadata is authored in an optional YAML front matter block at the beginning of .md/.markdown files. The shared parseMarkdownDocument boundary is used by the build generator, Konqueror preview, Article Reader, and safe search projection; it returns the body separately so front matter never becomes article text. The YAML parser is the small yaml dependency, rather than a regex-only metadata parser.

A valid front-matter title becomes the generated VFS file's effective displayName; its publication object uses the existing draft/published, slug, aliases, exact UTC publishedAt, summary, and ordered/case-sensitive tags rules. Front matter is one authoritative publication record. A legacy .kde3-meta.json publication remains a read-only fallback; front matter plus an unequal sidecar publication or title fails generation, and fields are never merged individually. Slugs remain explicit and are checked globally across front matter and sidecar sources.

.kde3-meta.json continues to own VFS identity, ordering, created, modified, and non-publication metadata. Normal generation, build, and development reconciliation are read-only with respect to authored publication metadata. scripts/migrate-publication-frontmatter.mjs is the explicit dry-run-by-default migration boundary; write mode copies legacy values, removes only displayName/publication, preserves generic metadata and article body, and validates the entire plan before writing.
